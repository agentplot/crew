# crew

Each drive's plan of bolts, its main level of Claude agents in herdr, and its bolts' work as Flume runs it.

- The drives are data in `~/.config/crew/teams.json` (version 6, which lists no team, its drives under `drives`, each named by its label alone and naming its `runs`, how each of its main-level roles runs, `standing` or `on-demand` as its Flume kind: see The main level and the console), written by the machine's configuration, crew's own module `services.crew` (from crew's flake, which the Boomdrive flake re-exports: see The flake) or another, or, on a host Nix does not configure, by `crew drive set` at Boomdrive's setup's asking (see State); crew refuses a file at any other version, version 2, 3, 4 or 5 among them, or one that lists teams, naming crew's own module, `services.crew`, `crew drive set`, or the machine's configuration that writes it as the fix, as every refusal of the file does, and doing nothing, and reads no former key; each drive carries its batch setting, `review: {after_changes, after_hours}`, and crew refuses one without it. Beside its drives the file may name the kept repositories of the host it is written on, `repositories`, each by its address, `<owner>/<name>`, with exactly its `dir` and its `checkout`, each an absolute path: on that host crew names them as the kit's folder, where worktrees are cut, and its checkout, the runner's container and view on a runner host, whether or not a drive's `repos` lists the repository, and refuses an entry of any other shape, naming the file. Where the file names none, a kit's folder and checkout are `<folder>/<name>` and `<folder>/<name>/main` in the folder of the first drive on that host whose `repos` lists it, and so they are on every other host; a host keeps no other repository. `repos` is a drive's list of addresses, `repositories` the host's map of each address to its folder and checkout. The teams file is the one file crew reads for a host's drives and the hosts that serve them, and crew reads no file of swancloud's or of any fleet's (record 0064): beside each drive's keys it gives `hosts`, each host crew reaches or reads, by the name `hostname -s` gives it, with exactly its `ssh` name and its `kind`, `darwin` or `nixos`, every drive's `machine` among them; for each drive, `folder`, the absolute folder of its herdr session on its machine, `repos`, the repositories that folder keeps there, each by its address, `<owner>/<name>`, possibly none, and `accounts`, the Claude account each of its five main-level roles runs under, two roles in one session naming one; and `consoles`, for the host it is written on, each drive whose console that host opens, by its label, with the absolute folder its tabs open in. A drive's first blueprints repo is kept on its machine, among its `repos` or in `repositories`. No field has a default, and a file lacking one is refused naming the key and the fix; a role's `session` is checked against no list of sessions, herdr running what the file names.
- `plugin/` is the same for every drive: the roles (`roles/`, each an agent definition naming its model and effort), the `crew` and `crew-role` commands (`bin/`), the builder that turns the teams file into briefs and settings (`lib/crew.py`), the plan (`lib/plan.py`, with `lib/gather.py`, which reads a host's kits, and `lib/transcript.py`, which checks a signal's excerpt against its agent's transcript), `crew sites` (`lib/sites.py`), and the skills. It installs as a Claude Code plugin; this repository is its marketplace.

## Bolts

```
crew fix      <bolt> <name> "<what is wrong>" [--label L]
crew fix      <bolt> <name> --drop [--label L]
crew answer   <work> "<words>" [--label L]
```

Any command, these and every other below, the internal `_` commands and those crew runs on another host among them, answers `-h` or `--help` among its own arguments with its usage and does nothing else, exiting 0: nothing is recorded, told, asked, launched, started or sent to another host. The usage is the command's own lines of `crew`'s usage, or its parser's for a command crew hands to one, as `crew bolt start --help`. A word that is not exactly `-h` or `--help` is a word, so `crew tell <agent> "--help with the tenant table"` tells it as any tell does.

A **bolt** is a body of work on the branch `bolt/<bolt>` on GitHub, a Flume **base place** of crew's kind `crew/bolt@1`, which `crew bolt start` launches on the kit's main, with no worktree, which moves only through sluice and then lands on main. `crew bolt start <bolt>` is the user's, or a proposal's the user approves: the planner proposes which bolts run, and no other agent starts one. Once a bolt is proven, every unit and chore merged and its verification green, it waits to land on the user's yes, a row of its kit's landings card, and a fix when its landing conflicts with main. A bolt is built from **units**, each one OpenSpec change, built in a Flume place of the change kind on the host whose runner's configuration names its kit's repository, which constructs, codes and verifies it and submits it to the bolt through sluice: sluice tests the bolt with it merged on the checks the kit's policy requires of its bolt branches, `[branches."bolt/*"]` in the `.config/sluice.toml` on its main, read from `origin/main`, and lands it as a merge commit only when they pass. `crew bolt start` makes no branch and reads no host: its plan write appends the launch of the bolt's base place, `bolt/<bolt>` of the kind `crew/bolt` on `main`, with no brief, before its pieces' launches, and Flume makes the bolt's branch on GitHub from the kit's main when the runner launches it, the kind landing with no stages of its own (`plugin/flume/kinds/bolt@1/kind.toml`, which crew writes whole into its kinds folder, `~/.local/share/flume/kinds/crew`, wherever it makes that folder, and which each runner host locks by its configuration). While the runner has not launched it, or refused it, the bolt's row says so in the runner's words, and `crew bolt start` again launches it anew with the pieces not yet launched. Every unit's, chore's and fix's place is cut from `origin/bolt/<bolt>` after a fetch and tracks it, so it holds every merge sluice landed there from any host. crew reads a bolt on GitHub where it lives, at `origin/bolt/<bolt>`, when the policy there names a remote for it: its head, its verification, the changes and chores it holds and every stage read from it, never the host's own `bolt/<bolt>`, which is sluice's copy and may lag GitHub's. `crew bolts` fetches the kit's origin first, a fetch that fails named in git's words and nothing read from the host's copy in its place; every other read, the rail and the board among them, takes the bolt as the host last fetched it. In a repository the host's teams file names, the runner's clone on a runner host, crew fetches nothing, and nor does any brief it writes: every read there, `crew bolts` and a landing's among them, takes GitHub's branches at origin's tracking refs as the runner last fetched them, which it does every pass and at once on a landing, and a read that needs them fresher waits for the runner's next fetch (agentplot/boomdrive `core.14`). A bolt started before bolts were base places, with no launch of `bolt/<bolt>`, lands under the crew that started it: its row has no box and says so, in `crew bolts`, on the rail and in main-level ops's band, and crew posts no land for it; a host's pin moves to this crew only once `crew bolts` names no such bolt there. crew starts no stage and waits on none: a stage's start and end are Flume's, read from the runner's records (see below).

A unit's, chore's and fix's places are Flume's: Flume makes each and has sluice equip it at the revision its launch read, `sluice equip`, with the tools the kit declares in its `.config/sluice.toml` and `.prototools`, as sluice equips every working copy it runs in (Flume's record 0036; sluice's clause 147). What runs there is said by the kind and the kit's own files, its `CLAUDE.md`, its `openspec/config.yaml` and its `.config/flume.toml`. crew readies no worktree, its landing's included, which sluice's submission equips as any submitter's. crew reads of a kit's `.config/sluice.toml` only what gates its bolt branches and where they live, through `plugin/lib/kit.py`, and nothing of a preview, which the runner asks sluice for; sluice reads the same file, which becomes `boomdrive.toml` once Boomdrive uses sluice's SDK.

A **fix** is a Flume place of the fix kind on a started bolt, `crew fix <bolt> <name> "<what is wrong>"`, the planner's or main-level ops's, cut from `bolt/<bolt>`, with no change and no plan record; a fix name already in use on the bolt is refused, as is a fix while the bolt's landing is queued (see below), and `crew fix <bolt> <name> --drop` drops it, a merged one refused, since a new fix undoes it. Flume submits a fix to the bolt as it submits a unit, through sluice; nothing of crew's moves a bolt's branch. A landing that conflicts with main is the bolt's: a fix merges main into its place, resolving the conflict, and is submitted to the bolt. crew removes no bolt's branch and no worktree for a bolt: a landed bolt's branch goes by Flume's tidy of its base place and sluice's close of `bolt/<bolt>`, and a dropped bolt's by the drop of its base place, sluice keeping one that holds work main lacks, named in Flume's answer, the user's to keep or delete (record 0003). Every place of Flume's, the main checkout and every other worktree crew leaves alone. A worktree crew made before bolts were base places, a landing's place `<kit>/places/land-<bolt>` or a bolt's worktree `<kit>/bolts/<bolt>`, is named by the tidy with the commands that remove it, `sluice release --worktree <path>` and then the kit's own `wt remove`, the user's to run, since crew runs neither.

A bolt may also hold **chores**: planned maintenance that changes nothing a spec says must be true and needs no decision, such as a tool or dependency bump, a pin or config aligned with another, the archive of a change whose every task is ticked, a rename, or a stale instruction or line of documentation. A chore has no OpenSpec change, no construct and no review: it is built in its bolt as a Flume place of the chore kind, each of its commits carrying a `Chore: <chore>` trailer, and submitted to the bolt through sluice as a unit is. `After` means for a chore what it means for a unit: it is launched only once what it comes after has landed on the bolt. A chore's stage is read from the runner's records as a unit's is, or, for one an older crew built, from the kit: `landed` once main's history holds its trailer, `merged` once the bolt's does. No batch ever holds a chore.

A wait of crew's, `crew review <label> --wait`, ends with the Claude session that started it, read by the process id Claude Code gives each command it runs (`CLAUDE_PID`): once that session is gone the wait ends at its next look, saying so and recording nothing; a wait run from a shell, or forwarded from another host, has no session to end with.

Every bolt's work runs through **Flume**, and the teams file lists no team and names no stream a kit's work runs in. crew runs no team's conductor, ops or slot: a started bolt's work runs in Flume places, which `crew bolts` shows. A start is refused for a bolt started already, but one whose own launch the runner refused, or while no runner answers for the drive, its state repository holding no `<label>/runner/<host>`, naming it; its one plan write marks the bolt `Path: flume`, writing no team, and appends to `requests.rec` (see State) the launch of the bolt's base place, main-level ops its recipient, and then a launch for each unit and chore, in the plan's order, in the kit's repository as the plan names it and naming no host or stream, cut from `bolt/<bolt>`, with its bolt's priority, the plan's first bolt the highest, the intent `<label>/<bolt>`, the drive's planner as its recipient and the work's own words as its brief, and starts no agent. crew looks up no kit's host: a **runner** (agentplot/boomdrive) whose configuration on its host (`~/.config/boomdrive/config.toml`) names the kit's repository and its folder there takes each, pulling it under a lease while its host's stream has room, and launches it through Flume in the stream its host's Flume configuration maps the repository to, which runs its kind's stages, construct, code and verify for a unit and code for a chore or a fix, and submits it to the bolt through sluice itself; a unit or chore that comes after other work is launched only once that work has landed on the bolt, the runner holding it meanwhile; the runner answers held too while it claims a launch or its stream has no room, so a launch with no `After` that the runner holds reads launching, with the runner's words, never held for its After work. Plan writes reach the places, each the write's own act in its own commit: a unit or chore added to or moved into a started bolt is launched; an approved amendment is a retry of the unit's construct with its words, or a drop and a new launch carrying them while its first has not run; a drop drops its place, and a dependent waiting on it is launched again without it; a reorder of bolts appends a priority for each place whose priority changed; a move out of the bolt, a split or an `After` change of launched work is refused, naming its place and drop then add as the way on. `crew answer <work> "<words>"`, the planner's, the design agent's or main-level ops's, appends a retry of the stage the work's place stopped short on or waits on its caller for, past its kind's bound or not, whatever stage it last delivered, or of its submission where that waits on its caller unheld, carrying the words, `<work>` the unit's or chore's name or a fix's place (`<bolt>--<name>`, `main--<name>`), and is refused, naming the place's stage, when it neither stopped short nor waits on its caller: a live place's stage as the runner that took it carried it, with that runner's host and when it carried it, since a wait Flume has told of since reaches crew with that runner's next carry, so the answer is given again once `crew bolts` shows the place waiting, never saying a live place has nothing to answer; or naming what crew could not read when it can't tell, as while the runner holds the launch or has carried none of Flume's status of the place; a stop-short whose agent Flume keeps open for its answer is answered so too, the retry naming its stage reaching that session as a tell answering it does. `crew fix <bolt> <name> "<words>"`, the planner's or main-level ops's, appends a launch of a Flume fix place on the bolt, `<bolt>--<name>`, with nothing held, in its kit's repository; `--drop` drops it, one merged refused; crew fix has no `--merge` or `--wait`, since Flume submits the fix to the bolt itself and `crew bolts` shows its stage; a fix in flight holds the bolt's landing. Where a bolt's base place names its landing fix, as crew's bolt kind does (`landing_fix = "flume/fix@1"`, `max_landing_fixes = 3`), Flume launches that fix itself, `<bolt>-<n>` on the bolt, on its own forecast of the bolt in conflict with main or on a landing it refused for a conflict or a failed check, and crew launches no fix and asks main-level ops nothing for it; once Flume has run its three, or its fix was dropped or could not be launched, crew asks main-level ops once in Flume's words and launches nothing, and ops starts the fix by hand. A started bolt whose base place names none, as on a host whose Flume is older than 0.19.0, and whose landing Flume refuses for a conflict with main, launches its take-main fix by the act that reads the runner's report of it, `<bolt>--take-main-<main's revision>`, with Flume's words, once however often the refusal is read, and its row says it takes main first; once that fix has merged and the bolt reads proven again, the user's send that ticked it still lands it.

## The plan

```
crew bolts [<bolt>] [--label L] [--json]
crew bolt  new <bolt> "<goal>" --repo <kit> [--source S]... [--before <bolt>]
crew bolt  start <bolt> [--label L]
crew bolt  order <bolt> --before <bolt>|--first|--last
crew bolt  drop <bolt> "<reason>" [--requeue]
crew bolt  land <bolt>
crew bolt  leave <bolt>... --excerpt "<the user's words>"
crew unit  add <unit> "<intent>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew unit  split <unit> "<narrowed intent>" --into <unit> "<intent>"
crew unit  amend <unit> "<new intent>"
crew unit  order <unit> --before <unit>|--first|--last
crew unit  after <unit> <unit>...|--none
crew unit  move <unit> <bolt>|queue [--unblocks <bolt>]
crew unit  drop <unit> "<reason>"
crew chore add <chore> "<what is done>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew chore order <chore> --before <unit or chore>|--first|--last
crew chore after <chore> <unit or chore>...|--none
crew chore move <chore> <bolt>|queue [--unblocks <bolt>]
crew chore drop <chore> "<reason>"
crew kit   rename <old> <new> [--label L]
```

Each drive keeps one recutils `plan.rec`, for all its kits, on its drive's branch of its state repository (see State). It holds only intent: Bolt and Unit records, in build order, a Unit record marked `Kind: chore` being a chore, its `Intent` its words, and a started Bolt marked `Path: flume`; a bolt names no team, and a `Team` an older crew wrote is read by nothing. A drive's kits are the repositories its plan's bolts and units and its run record's landings name, with no list of them anywhere else: a kit enters a drive with its first bolt or unit, in the plan of the drive the command runs as (`--label`, or the agent's own), and otherwise in the one drive whose plan or landings already name it. A name is taken once in a kit, by a unit or a chore: `crew unit add` and `crew chore add` refuse one the plan holds, one the kit's main has a change by, and one main's history holds a chore trailer for, read in the checkout the drive's main-level host keeps of the kit, and refuse any while that host keeps none, naming `crew kit rename` as the way on for a kit renamed there. They, and `crew unit split`, also refuse a name whose Flume branch stands, `change/<unit>` or `chore/<chore>`, read with git in each repository a launch of the kit's work would be made in, the folder the runner that took its work reports Flume cutting its places in and each runner's reported clone of it: Flume keeps a dropped place's branch while it holds work and refuses a launch that would make it again, so the add names the branch, where it stands and its commit, and the ways on, a fresh name, or the branch removed first by the planner or the user, never by crew; a kit no runner has taken work of and none reports keeping is not read, and one crew can't place is refused saying why. A drop of launched work says, as it prints and on its entry (`Note`), that Flume keeps its branch and the name stays taken while it stands. The `crew chore` commands take a unit's flags and make its refusals; there is no `chore split` or `chore amend`, a chore's words changing by a drop and an add, and a unit command on a chore, or a chore command on a unit, is refused naming its kind. A Source is a path in the drive's first blueprints repo, or `<owner>/<name>:<path>` in another. Every stage is read from the kits, one call per host. A command fetches the branch and reads each kit once on each host it runs on, however many steps it has, and a step that makes or removes a worktree leaves the next to read that kit again; a wait reads afresh each time it looks, and the host's follower and `crew events --follow` read again, at each look, only what has moved since they last read. A unit's tasks and planning mean what OpenSpec means by them, read from the change's files when it uses OpenSpec's spec-driven workflow and through `openspec` otherwise. A write fetches the branch over https into crew's bare cache of the repo (`~/.cache/crew/git/<owner>/<name>.git`), applies itself to the tip, checks each file it changed with `recfix --check` and the plan with crew's rules, commits through a temporary index, and pushes without force; a push refused because someone wrote first is applied again to the new tip, up to six times, waiting a growing moment before each fresh fetch, from half a second up to eight and 23.5 seconds at most in all, so a busy branch is outwaited; a write still refused says so, and a run-record entry so refused stays on the host for its next push. Nothing is ever merged. A write tells no agent of it.

A repository renamed on its forge is renamed in crew's records by one explicit command, `crew kit rename <old> <new>`, once its work is finished, never followed in flight and never its work dropped and added again (record 0060, `plan.22`): its work lands or is dropped, it is removed from the runner, Flume and sluice, it is renamed on its forge, crew's rename runs, and it is added back under the new name. The rename is the user's at a shell or a proposal's, which the planner writes and the user approves; the planner's own run is refused, naming `crew plan propose`, and every other agent's, naming the planner. It is refused, with nothing written and naming all that stands, while any of `<old>`'s work stands, matched by its name or `<owner>/<name>`: a bolt, unit or chore of the plan; a fix of its main or a role's work in it not landed or dropped; a place Flume holds live; a card open, or lost to its owner, under `land/<old>` or `record/<old>/<n>`; an unanswered batch holding its work that still waits; or an open proposal, but the one applying it, whose `Do` names it; what crew can't read of these is named as well. It is refused likewise while any host still keeps `<old>`, each host with a runner branch of the drive read with the drive's main-level host, by its runner's `repositories.rec`, or by what the teams file keeps there where the runner reports none, a host that is neither the one the file is written on nor one a drive runs on refusing it; no host needs to keep `<new>`, since the repository is added back under it after. And it is refused for two names of one repository, for a `<new>` that is a bolt's name, since `land/<new>` would name the bolt, and where no record of the drive names `<old>`. In one commit it renames `<old>` to `<new>` in every record a reader matches the repository by: the plan's Sources that name a decision record in it, each request's `Repo` in `requests.rec` and a fix of its main's `Work`, and the run record's entries on the drive's branch, their `Repo` and each object of their `On` and `From` built on the name, `kit/`, `land/`, `queue/`, `record/<old>/<n>` and `fix/main/<old>/<name>`; a field keeps its form, `<owner>/<old>` becoming `<owner>/<new>` unless `<new>` is an address. Its `kit.rename` entry names both, `On: kit/<new>` and `From: kit/<old>`, with `Repo` the new name and `Count` every record renamed. It leaves as written what no reader looks a repository up from: Goals and Intents, a Source naming no decision record, `proposals.rec`, signals, `moves.rec`, `asks.rec`, `roles.rec`, an entry's `Key`, `Why` and `Refused`, every earlier `kit.rename` entry, the runners' branches and each host's own run-record files; it rewrites a file record by record, its descriptor, comments and order kept, and leaves a file it renames nothing in byte for byte. It appends no request and launches, retries or drops nothing. `<old>` may be any name a record still holds, so running the rename again renames what an earlier one left, and before it reads the branch it pushes the entries its own host kept unpushed, so they are renamed with the rest. A drive is never renamed: no crew command renames a label, and a label that changes in the teams file is one drive removed and another added, the new label's state its own branch, `<label>/main`, and a command naming the old label refused as naming no drive. Every record is read as written, its repository by the name it holds: no reader maps a former name through `kit.rename` entries, and `crew bolt new --repo`, `crew unit add --repo` and `crew chore add --repo` write the name they are given.

A unit's stage, as `crew bolts` shows it and `--json` gives it in `stage`, is the first that holds of `landed` (main has its change), `merged` (its bolt holds its change archived, as its own merge leaves it), `verify` (every task ticked), `code` (some ticked), `planned` (its planning complete), `construct` (its worktree exists), and `ready` or `waiting` by whether each of its `After` units has finished construct; a unit with no bolt is `queued`. A unit whose change its bolt holds open, carried there inside another unit's merge, has not merged: it reads at its own stage, from its place or, once that is gone, from the change on the bolt, keeps its place, and its own merge is owed; that merge makes its place again from the bolt when it is gone. A unit's or chore's merge is refused while its branch holds another unit's change open that the bolt does not hold archived, naming it. A unit the plan marks `Amended` reads, after `landed` and `merged`, `amended` until construct is run again, then `construct` until that commits, whatever its tasks say; then the mark stops counting, the unit reads from its tasks again, and the write that records that construct's end clears it.

A unit, chore or fix of a bolt marked `Path: flume` reads its stage from the records of the runner whose answers hold its launch (see State), never from the kit: `launching` until the runner answers its launch, `waiting` while the runner holds it for its `After` work, `refused` with the runner's words; then from Flume's status of its place, as the runner carried it: `queued` for room at a stage; `construct`, `code` with its ticked tasks of all, or `verify`, while that stage runs; `needs` with the agent's question when it stopped short; its stage with sluice's words when sluice sent it back; `submitted` with sluice's number; `waits` with Flume's words and the stage it waits to retry, or its submission, whenever it waits on its caller for a retry, past its kind's bound among them, whatever stage it last delivered; `stalled` once Flume says the place is stalled; `merged` once its place has landed on the bolt, `landed` once main holds that commit; and `dropped`. A piece's end is the runner's report alone: a place Flume has tidied reads as the record Flume holds for the runner after its tidy, which the runner carries as the place's status until its report holds it, `merged` at the commit it landed at, `landed` once main holds that commit, or `dropped`; a place tidied before its host's runner carried its end reads as the runner last carried it, `submitted` for instance, until it is dropped by proposal; and a launch the runner refused because the bolt already holds the change reads `refused`, in the runner's words. No landing commit on the bolt or on main is read for a piece. A fix is read as any piece, and one the runner reports merged holds its bolt's landing no longer, its drop refused as a merged fix's is. A runner whose branch can't be read is named, and the work no runner crew read has taken reads `unknown`, as does work two runners took, naming both. Where a started bolt's work runs is what the runner that took it reported: the host whose runner took the newest of the bolt's launches it has taken, and the kit's folder there as that runner's `repositories.rec` names it for the kit as the plan names it, or, where the runner reports no repositories, as Flume's status of its newest place of the kit names it, the bolt's work first and then the kit's other work, never another host's, and the stream its work runs in as Flume's status of its newest place of the work names it, none while it carries none; a runner that reports no repositories is not refused for that alone, and leaves the kit unread, naming its host, only while it also carries no place of the kit naming the folder, and one that reports its repositories but none for the kit names what it keeps and `crew kit rename`; while no runner has taken any of the bolt's own work, it runs where the runner that took its kit's newest work reported the kit; crew reads, lands, previews and sweeps the bolt there. A landed bolt closes once each of its units and chores reads `merged` so, as the runner reports its place's end, at a commit its kit's main holds, whether or not its branch stands: `crew bolt land` closes it then, and a piece that does not read so keeps it open, named with its stage. `crew bolts` says it on the bolt's head line, `@ deneb, in Flume stream madswan`, and gives a piece's line its place's folder and what goes with its stage; `--json` gives each bolt its `host` and `stream` and each piece of a started bolt its stage under `flume`, and names each runner it could not read in `runners_unread`.

While a piece's submission stands in sluice, `crew bolts` shows it on the piece's line from the first read after the runner reports it, whoever submitted it: a unit's, chore's or fix's merge into `bolt/<bolt>`, `submitted #41`, as Flume's status of the piece's place gives it and the piece's runner carries it; and the bolt's landing on its kit's main on the bolt's head line as the runner reports it beside what the run record holds, `landing asked, request 57`, then `landing #412 under test`. `--json` gives each piece's stage as the runner reports it under `flume`, a submitted one's `submission` its number, and the bolt its base place's facts as the runner reports them, `base`, its landing so read, `landing`, and its `landing_record`. crew reads neither from sluice's queue and runs no sluice for them (crew record 0056), so a session that comes back after a restart finds its submission on the row for as long as the runner carries it; a runner that can't be read is named, and the stages of its work read unknown.

A bolt's landing is read from the runner's report of its base place, beside the run record, and said in words of its own on the bolt's head line in `crew bolts`, on the rail and on the board:

- **asked**, from the land crew posted on the user's send until the runner's report decides it: `landing asked, request 57`.
- **submitted**, once Flume has submitted the base place to main, with the merge queue's entry and its state: `landing #412 under test`.
- **landed**, at the commit Flume names, `landed at <commit>`, the bolt then closed by the act that read it.
- **refused**, for the bolt's own content, a check that failed or a conflict with main, in Flume's words, and once recorded, while the bolt's head is the one refused, `landing #<n> rejected at <head>, open for work: <Flume's words>`.
- **stopped**, by the runner or by Flume for nothing of the bolt's, in their words, the send that ticked it spent.
- **none**: never asked, or asked again on a new send; an older crew's `queued` and `landing again` entries read as they were.

A bolt started before bolts were base places says instead that it lands under the crew that started it.

While a bolt's landing is asked, submitted, queued or landing again, no work joins it, since Flume lands the bolt's branch as it stands and work merged into it meanwhile would be left out of main. `crew unit add`, `crew chore add`, `crew unit move` and `crew chore move` into the bolt, run directly or in a proposal, and `crew fix <bolt>` are refused, naming the landing. The rail leaves such a bolt out of those that can land. Once the landing is refused, the bolt is open for the work that answers it: crew's take-main fix for a conflict, ops's fix for a failed check, and new units. `crew bolts --json` gives each started bolt its `landing_record` and its `landing`.

A unit in flight is amended with `crew unit amend <unit> "<new intent>"`, which the user runs at a shell and the planner only inside a proposal, and its revised change is in the drive's next batch: it replaces the unit's intent, and a unit that has a worktree is marked amended (`intent`, or `proposal/<n>` from an approval). In a started bolt the write reaches the unit's place itself: a launched place gets a retry of its construct carrying the amendment's words, the planner's case among them for a proposal, and a launch the runner holds or has not answered is dropped and the unit launched anew carrying them. A unit that has merged is refused: a defect in it is a fix, and new work is a new unit.

`crew bolt drop` removes a bolt and its units and chores from the plan, or with `--requeue` queues them, either way dropping in its own commit each of the bolt's launches still standing, a requeued unit's among them, so a requeued unit is launched afresh in the bolt that next starts with it, and last the launch of its base place, which Flume refuses while a place on its branch is live; a base place whose drop the runner refused is asked again by the next plan write that finds the bolt gone from the plan, its launch standing and no piece of it live, once for each refusal. crew deletes no branch: a dropped bolt's branch that holds work main lacks is kept by sluice and named in Flume's answer, which the runner carries, the user's to keep or delete. A bolt started before bolts were base places drops its pieces' launches alone and asks nothing for its branch, which stays, named, the user's.

A bolt lands on the user's send of its row on its kit's landings card, and on nothing else: crew carries the send to the runner itself, at its next raise of the card, as one `land` request of each ticked row's launch, in the card's order, a fix of main's first, once for each send and head, each recorded as a `bolt.submit` or `fix.merge` entry naming the card, the head, the request and `Outcome: asked`, in main-level ops's name, with no agent running anything; a row taking main first, stopped, or started before bolts were base places gets none. The runner has Flume submit the bolt's base place to main through the merge queue, which tests main with the bolt merged on the checks main's policy requires and lands it as a merge commit on GitHub's main only when they pass, so nothing is refused for the host's own main lagging GitHub's. A landing pushes nothing and levels no host's checkout: every kit's main checkout is an anchor at GitHub's main that the fleet's timer moves within minutes, which crew never moves. Its outcome is read from the runner's report by the first act of crew's that reads the bolt, on any host, and recorded once. Landed, the read closes the bolt by `crew bolt land`'s own code in ops's name, its `bolt.land` entry naming the kit and the commit Flume names (`Repo` and `Head`), from which a deploy's view tells the bolts it carried, and its age in whole minutes from its newest start to that entry (`Age`) and those minutes by holder, as its head line on the board splits them (`Split`), read from the run record; it ends the bolt's reading, lets go its preview on its host, and raises its kit's landings card, which closes once every bolt the user ticked has landed or been held, "Landed on GitHub's main: <bolt> at `<sha>`; every host's folder follows by swancloud's timer within minutes". Where the bolt's base place names a landing fix, the row is held with no box for it, saying which fix takes main in or makes the failed checks pass, that Flume launches it, or that Flume ran its landing fixes and the bolt waits on ops (see Bolts). Where it names none, refused for a check that failed, the row is held with no box, in Flume's words, for a fix on the bolt that main-level ops starts with them; refused for a conflict, the read launches the bolt's take-main fix (see Bolts), once however often it is read; once either fix has merged and the bolt reads proven again, the send that ticked it stands where the bolt's own work is unchanged. Stopped, by the runner or by Flume for nothing of the bolt's, the row keeps its box with their words and the send is spent: the answered card closes naming it stopped, and the card that follows asks for it again. A refusal or a stop asks main-level ops where it runs as its kind, and an outcome crew can't tell is said and records nothing. `crew bolt land <bolt>` on a started bolt is refused, recording nothing, naming its landing's outcome, until the runner reports it landed, no landing commit on its kit's main read for it, and a bolt started before bolts were base places is refused, closed only by the crew that started it; a bolt never started, built outside crew, lands by it on the user's word once main holds each of its units' changes and chores, read in the checkout the drive's main-level host keeps of the kit, with nothing to merge. `crew bolt submit`, with any arguments, is refused at once, before it reads anything, naming the card's send as the way, and the user's words in main-level ops's pane are no word to land: ops answers them by pointing to the card.

A kit's main that fails its checks after a landing is fixed by a fix on main, not a reopened bolt. `crew main fix <kit> <name> "<the failure's words>"`, main-level ops's or the user's on reading main red, appends a launch of a Flume fix place on main, `main--<name>` (`fix/main/<kit>/<name>` in the run record), its brief the failure's words, its submission held for the user's word, main-level ops its recipient, ahead of every bolt, in the kit's repository and naming no host or stream, for a runner whose configuration names it to take. Once its code has delivered and its submission waits held, the kit's landings row on the rail carries it, `fix main--<name>` with the failure's first line, beside the bolts that wait, and the user's send of that row lands it: crew carries it to the runner at its next raise of the card as a land of the fix's launch, ahead of the bolts the same send lands, once, recorded as a `fix.merge` entry with `Outcome: asked`; the runner submits it, the merge queue lands it on main and the row leaves. `crew main fix <kit> <name> --send`, with or without `--excerpt`, is refused at once, before it reads anything, naming the send of the fix's row on the kit's landings card as the way. `--drop` drops it, one landed refused. Where no runner answers for the drive, it is refused, naming the way until then: a bolt of one chore, proposed first among the planned.

## Proposals

```
crew plan propose <file> [--replaces <n>]
crew plan proposed [<n>] [--label L] [--json] [--open]
crew plan approve <n> [--clear <unit>...]
crew plan answer <n> <question> <answer>... [--note "<text>"]
crew plan drop <n> "<reason>"
```

The planner changes the plan only by a **proposal** the user approves: where new work goes (a new bolt, a unit in a bolt, the queue), and every move, split, amendment, reorder or drop. A proposal is a record in `proposals.rec` on the drive's branch: the planner's `Case`, and the plan commands it would run, in order, one `Do` each, as typed without the leading `crew` (`bolt new|start|order|drop`, `unit add|amend|move|split|order|after|drop`, `chore add|move|order|after|drop`, `kit rename`). Proposals are numbered, and never removed or changed.

- `crew plan propose <file>` takes a file of one record, a `Case` and its `Do` lines. Each command is checked in order against the plan as the ones before it leave it, with every refusal it has run directly; a refused command refuses the proposal and nothing is written. A proposal is also refused, with nothing written and no card raised, when a bolt it creates, or a unit or chore it adds or moves into a bolt, names as a source a decision record (`docs/adr/<number>`, of its kit, or of the repository written before it as `<owner>/<name>:`) that its main on GitHub does not hold accepted, naming each record and what main holds: proposed, rejected, accepted with an amendment still marked proposed, no status, or no such record. It waits on the user alone, and no agent is told of it. `--replaces <n>` drops proposal n and writes its successor in one commit. Once the proposal is written, crew raises its Pending You card itself, in the planner's name, keyed `proposal/<n>` of the first proposal of its chain (the one each `--replaces` follows back to), and prints the line the planner adopts it with; a rewrite changes the chain's one card, "Rewritten as proposal <n> after your note", in place while it waits on the user, and once the user's note answered it, by acking it with that note and posting the new version following it; a card whose rows fill more than one list asks them as questions, which Pending You never changes in place, so a rewrite withdraws it with the note while it waits and posts the new version following it, as does a rewrite that moves the card to another form, a hold-to-approve, a choice, one list or lists; the rail's row for the successor carries the chain's key. A proposal the user writes has no card. The card asks only the units and chores the proposal makes new to a bolt or the queue, in one checkbox list, each a box ticked as proposed, which the user clears to leave it out; what else it changes, a drop, an amendment, a move, an order or a new bolt, is drawn on its face and applies with it, as its summary says. A lone new unit is the choice of its two sides, and a proposal with none a hold-to-approve, which the user declines with a note to keep what it drops or amends. A card Pending You refuses refuses nothing of the proposal.
- `crew plan proposed` lists the open proposals and what each waits on; `crew plan proposed <n>` prints one as markdown: the case, then each change in plain words, a unit's intent beside what it rests on (a signal's assertion and excerpt) and the goal of the bolt it would join and whether it is started, and an amended unit's bolt, whether it is started, and its stage, its intent as it stands and as proposed, and what approval sets in motion; under each change, the command approval runs; and, for an open proposal, who it waits on, in words. It reads only the branch, so any host can answer. With `--open`, it writes that page to `~/.local/state/crew/proposals/<label>-<n>.md` on the host it runs on and opens it in plannotator, for the user to read and annotate: beside the caller in herdr, inline in the terminal otherwise.
- `crew plan approve <n>` applies the proposal's commands, as read, to the plan at the tip and closes the proposal, in one commit, or changes nothing when one no longer applies. A unit or chore with a worktree that moves is rebased before the push and put back if the approval is refused. With `--clear <unit>...` it leaves out the new units and chores the user cleared and every command that concerns only one of them, so a cleared unit is never made and one moved in from the queue or another bolt stays where it was; it refuses, changing nothing, a cleared unit the proposal does not make new to a bolt, and a command left in that names a cleared unit, for the planner to write the proposal again; and it records each as `Cleared` on the proposal. The user runs it, or an agent on the user's word. crew then closes the proposal's card with what was applied and what was left out, and tells the planner the same when someone else approved it.
- `crew plan answer <n> <question> <answer>...` records one answer of open proposal n's card, as the planner reads it: `rows-<k>` and the ids of the boxes the user left ticked (`rows-1` for a card of one list, and for a lone new unit the side picked), or, for a hold-to-approve, `plan approve` or `plan decline`, with `--note` for the user's note. It checks the answer against the card crew builds for the proposal, refuses an answer that differs from one it holds, and keeps the answers in `~/.local/state/crew/cards/<label>/proposal/<n>/answers.json` on the host it runs on, the planner's, never on the branch. Once it holds every question's answer, it applies the change with the boxes as they stand, as `crew plan approve` does: a new unit unticked left out, as `--clear` leaves it, and recorded as `Cleared`; and it prints the note as the user's word for the planner's next proposal. A decline applies nothing. Either way the answers go.
- `crew plan drop <n> "<reason>"` closes a proposal unapplied, with the reason, and crew withdraws its card with it, or, once the user answered the card, closes it as dropped on their note, since their note may ask them something, which Pending You refuses as a close's outcome.

Work a bolt in flight needs before it can be proven or land goes into that bolt: a `unit add` or `unit move` marked `--unblocks <bolt>` must place the unit in that held bolt, where it goes ahead of the first unit not yet merged, and the mark is shown on the proposal.

Who writes the plan directly, when the command runs as an agent crew started (`CREW_AGENT`):

| Agent | Writes directly | Otherwise |
|---|---|---|
| the user at a shell | everything | |
| `<label>-planner` | proposals | refused, naming `crew plan propose` |
| `<label>-design` | `unit add … --repo <kit>` and `chore add … --repo <kit>`, the queue | refused, naming the planner |
| `<label>-ops` | `bolt land` | refused, naming the planner |
| any other agent | nothing | refused, naming the planner |

`crew bolt start` is the user's alone outside a proposal, which the planner proposes and the user approves; any agent running it is refused, naming the planner and the user. A proposal waits on the user alone.

The three commands that write a runner's requests rather than the plan, the user's at a shell, are refused from any agent but these: `crew answer`, the planner's, the design agent's and main-level ops's; `crew fix` on a started bolt, the planner's and main-level ops's; and `crew main fix`, main-level ops's. A request's `By` names who ran it.

Every refusal is a run-record entry. Writing, approving and dropping a proposal are entries naming `proposal/<n>`, and each change an approval applies is an entry of its own, from the proposal, with the approval's commit; `crew trace` follows them.

## State

```
crew state init <label>
crew drive set <label> --state <owner/name> --blueprints <owner/name>... --machine <host> --session <name> --folder <path>
    --repos <owner/name>... --accounts <role> <account>... --runs <role> standing|on-demand...
    --review <after_changes> <after_hours> --hosts <host> <ssh> <kind>... [--roles <role> model|effort|session <value>]... [--console <path>]
    [--repositories <owner/name> <dir> <checkout>]... [--json]
```

A **drive** is a body of work: its main level, its kits and its loop, named by its label. Its state is the files on one branch, `<label>/main`, of the state repository the teams file names for it (`state`, one per organisation, such as `WilldanGroup/crew-state`), apart from the design:

- `plan.rec`, the plan;
- `moves.rec`, every signal's one move;
- `proposals.rec`, the planner's proposals;
- `signals/<capture>/`, the captures and signals recorded through crew (see Signals);
- `runs/<host>/<YYYY-MM-DD>.rec`, the run record, each entry pushed by the host that wrote it as it is written;
- `requests.rec`, crew's requests of the drive's runners for a started bolt's work, each kit's launch naming its repository for a runner whose configuration names it (see Bolts), and for a role's run's work that lands (`crew role land`), naming its host and stream: a launch of a Flume place, a retry with words, a drop or a priority; and a confirm, which a role's run's end appends for each launch whose place's ends its turn took, naming the launch, the role's address and each end's delivery key, for the runner that holds the launch to confirm to Flume as that role (`crew role end`); numbered from 1, each appended in the commit of the plan write that occasions it, recfix-checked with crew's own rules, and never changed or removed;
- `asks.rec`, what waits on each main-level role that runs as its kind (see The main level and the console): an **Ask** for each thing that names the role, numbered from 1, with `Role`, `From`, `What` (`tell`, `send`, `capture`, `landed`, `card`, `open`, `batch` or `delivered`), the record it `Names`, the `Key` it is written once for, its `Words` and `At`; and a **Turn** for each start of a role's run that took something, numbered from 1, with the run, its place and host, a `Took` for each ask or waiting place it took, `Began`, and `Ended` with what the run `Said` it did, or `Superseded` by the turn that took its asks again;
- `roles.rec`, one **Role** record for each role a drive runs as its kind, written to match the teams file by `crew main up` and in the commit of any ask whose role's record is missing or differs: its `Address` (`<label>/<role>`), `Run`, `Host`, `Repository` (the drive's first blueprints repo), `Kinds`, `Kind` (`crew-<role>`), `Name`, `Stream` (the drive's own, named by its label), `Priority`, `Intent`, `Model` and `Effort`, from which each host's runner launches the role's run.

Each host's runner answers on a branch of its own in the same repository, `<label>/runner/<host>`, which only that runner writes and crew never does: `runner.rec`, naming the host, the runner's version and since when it serves the drive, so a branch that exists says a runner answers there; `answers.rec`, its answer to each request it has read, `held` while a launch waits on its `After`, `launched`, `done` or `refused`, with the place's path and Flume's or its own words; and `places.rec`, Flume's status of each place it launched as `flume status --json` gives it, kept after Flume tidies the place until its work has left the plan, and a `Run` for each role's run, keyed by the role's address, `<label>/<role>`, with its place and status, or the runner's words where it could launch none, which `crew role open`, `crew main status` and the board read; and `repositories.rec`, each repository the runner keeps on its host by its forge address with its clone's folder, where crew reads a kit's folder there, a branch with none reporting no repositories, whose kits crew reads in the folder its places name. crew fetches `<label>/runner/*` in the same fetch as `<label>/main`, into the same cache, and reads each host's files at the tip it fetched; a host with no branch is no runner and hides nothing, and one whose files recfix refuses, or crew can't read, a `repositories.rec` naming no address or one twice among them, hides only the work no runner crew read has taken, which reads `unknown`, naming it.

Drives sharing a repository never meet: each command fetches and pushes only its own drive's branch, and no branch shares history with another. A write that changes several files is one commit, and every write is an act whose commit carries its entry: the entry of the act, and of each ask and further act the write holds, is added to its host's day file under `runs/<host>/` in the write's own commit, made again with it whenever a refused push applies it to a new tip, and named in the commit's `Crew-Entry:` trailers; such an entry names no commit of its own, since the commit carrying it is its commit. crew refuses a write that names no act, since its commit would name an entry nothing writes. So the branch never holds an act without its entry, and a decision reads the branch at its tip. A commit an older crew wrote in two steps, its act and then its entry as the commit after, is read at the tip like any other, its entry joining the run record when it arrives. `crew state init <label>` creates the branch: it adopts the first blueprints repo's `plan/<label>` with its history where there is one, joins another blueprints repo's `plan/<label>` in one commit naming where it came from, and copies the first blueprints repo's `signals/moves.rec`; run again, it finishes what a stopped run left, or says the branch exists. A clone of the branch reads with `recsel` and nothing else.

`crew drive set <label>` names a new drive on a host Nix does not configure, as Boomdrive's setup runs it on a person's Mac once it has made the state repository on GitHub, and makes its state. Every key crew's module writes for a drive, and for the hosts it needs and this host's console and kept repositories of it, is a flag named as the file names the key, with no default: `--state`, `--blueprints` (once or more, the first the drive's default), `--machine`, `--session`, `--folder`, `--repos` (once or more), `--accounts` and `--runs` (once for each of the five main-level roles, `--runs <role> standing` or `--runs <role> on-demand`), `--review <after_changes> <after_hours>` and `--hosts` (once or more, the drive's machine among them) are required, and `--roles`, `--console` and `--repositories` are not; a flag that takes several words takes them as separate arguments. A flag left out, given past its count or given a value crew does not accept is refused naming it, before anything is read or written, as are a first blueprints repo not among `--repos`, a machine not among `--hosts`, a kept repository not among `--repos`, and `--repositories` for a drive whose machine is another host. It runs on the host it is invoked on and is never forwarded. It fetches `<label>/main` first, refusing a repository it cannot fetch from with nothing written, an empty repository reading as one with no branch; then, under a lock on `~/.config/crew/`, it writes `~/.config/crew/teams.json`: the drive's entry replaced whole by the flags', each host `--hosts` names set, the drive's console set or removed, each kept repository given set and one the file holds kept only while another drive of this host lists it, and every other drive, host, console and key kept as the file holds it; the file is written as crew's module writes it, keys sorted, no space and no newline, its drives in the order of their labels, so a host reads the same bytes whichever wrote it, by a new file renamed over the old. The file it would write is checked as crew loads one, and one crew would refuse is refused in crew's words with nothing written. A file crew cannot read at all, one that is no JSON, holds no object, or is at a version this crew does not read, is moved aside once, to `teams.json.before-drive-set`, both paths named with why, and refused with nothing written where that path is taken. A file at crew's own version is crew's own, written by this command or crew's module, and is never moved aside, since that would drop every other drive of the host. The set mends what it replaces: such a file is written wherever every check passes once the drive's entry and the hosts, console and kept repositories its flags give are set, whatever it held for them before. Where a check still fails, as for another drive's wrong field, or a part of it is of a shape the set cannot keep, a `drives` that is no list of objects or a `hosts`, `consoles` or `repositories` that is no object, it is refused in crew's words, naming the check or the key, the file and every drive it names left as they are, with nothing written and nothing moved. Where the teams file is a link, as Nix makes it, nothing is written there: the command says so, naming where it points, and goes on to the state only where the linked file names the drive with every fact the flags give, refusing otherwise, naming each key that differs and `services.crew.settings.drives.<label>`. It then makes the drive's state by `crew state init`'s own steps, leaving a branch that exists as it is. Where it changed a key of the file, one `drive.set` entry on `drive/<label>` names each key by its path and never its value, written to this host's run record once the file is, before the state is made, and pushed to the branch with the state: with its first write where the branch is new, and by the command's last act, which pushes whatever of this host's record of the drive the branch lacks. Where the state is not made, a push refused among the reasons, the command is refused saying the teams file names the drive as given and that the same command again makes its state, recorded as a refused `state.init` on `plan/<label>`; this host keeps the set's entry, and the run again makes the state and pushes that entry first, so the branch says who named the drive however many runs it took. Run again with the same flags once the state is made, it changes no byte of the file, pushes no commit and writes no entry. It answers one line for the file and one for the state, a moved file's line first, or with `--json` one object: the label, the file's outcome, `written`, `unchanged` or `linked`, the path a file was moved to and the keys changed, and the state's, `made`, `finished` or `exists`, with its branch's tip.

## Signals

```
crew signal <slug> "<what it asserts>" --excerpt "<the words, verbatim>"|--excerpt-file <path> [--kind K] [--subject a,b]
crew signal show <id>
crew signal move <id> attach|challenge|new-territory|answered|drop [--target T] [--reason R]
crew signal land <capture-dir> [--label L]
```

A **signal** is one thing noticed, with the words that show it, in the shape the blueprints' `signals/README.md` gives: a directory per capture, holding `capture.md` and one file per signal. Signals have two homes. What the agents and the user record with `crew signal` is under `signals/` on the drive's branch of its state repository; what the daily pass reads from meetings and channels stays under `signals/` in the drive's first blueprints repo. An id is unique across both, and every command looks it up on the drive's branch first.

An agent crew started gives an **excerpt**: the words that show the finding, copied as its session received them, from the user or from a tool's output (`--excerpt-file` for words the shell would mangle). crew looks for them, whitespace aside, in the agent's own Claude transcript, `~/.claude*/projects/*/<session>.jsonl` for the session herdr names for the agent, and records a grade on the capture:

- `verified`: the words are in a record the session received, and the capture says who asserted them: `user`; `tool`, for a command's output; `agent:<name>`, for what another agent sent with `crew tell`; or `crew`, for crew's own notice;
- `found`: they are in the transcript, in a record crew cannot classify;
- `unverified`: crew could not read the transcript, and the capture says why: herdr names no session, there is no file, its lines are not JSON, or it has not been written for 15 minutes, so crew may be reading another session's.

A signal is refused only when the transcript is the live session's, its last record written within 15 minutes, and the words are nowhere in it but in what the agent wrote itself: a paraphrase. The refusal says so, and names the other way words a tool printed can be missing: a background task's output reaches the transcript only once the agent has read the output file its task notification names, so the agent reads that file and records the signal again. A change in Claude Code's format lowers a grade and never stops a capture, and no command refuses anything for its grade; the grade is shown wherever the excerpt is.

A capture is the one record the excerpt came from. Its `capture.md` names the host, the Claude session, the record and its time, who asserted it, and where the agent was working: the main level, for a main-level role. The record itself is copied to `~/.local/state/crew/<label>/raw/<capture>.jsonl` on the host, and the capture points at it as `<host>:<path>`; of the source, only the excerpt enters git. A second signal from the same record joins its capture as its next signal, and the same signal again writes nothing. The capture and its signal are one commit on the drive's branch. The user's own note, `crew signal` at a shell, is its own excerpt (`excerpt: own`), of kind `ask` unless another is given.

A program records its own captures, a kit's deployer one per failed deploy, an adapter watching the tools the fleet pins one per newer upstream version, and hands each to crew with `crew signal land <capture-dir> --label L`, run as the program (`CREW_AGENT`) on the host that ran it. The folder holds `capture.md` and its signals, `NN-<slug>.md`, and nothing else; the capture names itself, the program as its `source`, who captured it, its event's date and its raw record, `<host>:<path>`, which must be on that host, since only the excerpt enters git; it is read, and counts its signals, at least one, made by the program with no model between: the capture is its own excerpt. Each signal names itself, its kind and who asserted it, says what it asserts, quotes its excerpt, and is no larger than 8 KiB, the program cutting its excerpt to fit and keeping the whole in the raw record. A capture whose name is not crew's kind of name, lowercase words, digits and dashes, is refused. crew lands the folder whole on the drive's branch in one commit, as a `capture` entry naming each signal; files the branch holds already are passed over, the same capture again prints that it is already landed and writes nothing, and a capture or signal there that differs is refused, since neither is ever changed. A program never writes a blueprints repo, and `crew signal land --help`'s first line is its usage, which a program reads to know this crew takes captures.

`crew signal show <id>` prints a signal, its capture's fields (the grade, who captured it, where and when, the session and the raw record) and its move, from any host. Every command that takes a signal's id, `show`, `move`, `--signal` and `crew trace signals/<id>` among them, takes its full id, `<capture>/<NN>-<slug>`, or its short one, `<capture>/<NN>`, which names the one signal of that capture numbered NN. Curation's moves, `crew signal move`, are appended to `moves.rec` on the drive's branch, and a signal becomes work only through its `route` move, which `crew unit add --signal` writes in the same commit as the unit, and `crew chore add --signal` with the chore. Each signal has one move, and nothing is ever merged.

What crew sends an agent is marked as crew's: `crew tell` sends `[crew tell from <sender>] <text>`, the sender being the agent or `<user>@<host>`, and crew's greetings and notices send `[crew] <text>`, so neither is taken for the user's typing. A word the user sends from a dock of the board reaches its item's agent through `crew tell --board`, which reads the word as the board's listener posts it, `{"label", "key", "to", "text"}` on its standard input, refuses one that is not of that form, names no drive crew knows, is on a key of no dock's kind, is for an agent its item's kind does not go to in that drive, or is empty, over 1000 characters or more than one line, and sends `[crew tell from <user>@board] (on <kind> <name>) <text>`, `<user>` being whom the listener runs as, printing `sent to <agent>`; a tell it can't make types nothing and says why in the tell's own words. It is recorded as any tell, with its length and never its text. A tell from `<user>@board` is the user's word on the item it names, and a signal captured from it is the user's, but it answers nothing: crew never takes words that reached an agent only from the board as the user's word to land a bolt, answer a batch or settle a record in a pane, saying the words came from the board and where the user answers instead, and the same words typed in the pane, or told from the user's shell, still count. Every brief says so beside its roster.

## Operations


The operations on a drive's environments, a deploy being one kind. A landing deploys nothing; a kit's deployer, or a hosted CI/CD in its place, deploys main under each environment's policy (ADR 0012, `plan.14`), and these are what it asks of crew, each run where the drive's main level runs, as the one asking, on that host's run record (`ops.*` entries on `env/<env>`); an offer run on another host carries its files' text there. `offer` makes a `manual` environment's deploy of a commit a row under *operations* on the rail, keyed `deploy/<env>`, and crew raises its card in main-level ops's name, telling ops the line that adopts it: on its face the kit's notes for the range from the environment's last deployed commit, as the kit's changelog tool wrote them and the deployer hands them with `--notes <file>`, and the range's after-deploy steps with their doers, one a line as the deployer gathers them (`step <n> <doer> <when> <environments> <why> <text>`, tab-separated, `held` among the when words), with `--steps <file>`, and before them all, ahead of the notes, the steps of the user's the deploy waits on, `before` among their when words (swancloud record 0038, record 0059): each with why, a box for the user to tick once it is done and one for the deploy, the card then boxes held to send, never a hold-to-approve, until every such step is done; handed no notes, the landings the range carries: the first-parent commits of the kit's main from the environment's last deployed commit to the offered one, read with git where the main level runs, a landing of sluice's by the subject of the branch it merged and one the run record holds by its bolt, or what git could not read. crew writes none of the notes, keeps the files beside the offer on its host and none of their text in the run record, and refuses a file it can't read, offering nothing. The card follows the environment's last deploy card when the user declined it, and otherwise no card: never a landings card, whose landings the deploy carries on its face. The same offer again writes nothing, and posts the deploy's card again when main-level ops holds none open, as when Pending You refused it; handed other notes or steps, it changes its card in place; a newer one replaces it and changes its one card in place. The user's word is holding that card, recorded with `approve` for the commit the row shows, and refused for any other; for a deploy that waits on steps of the user's, the word is the card's send with every box ticked, `approve --ticked <n>,...` naming the steps ticked by their numbers on the card, each recorded done on the step its deployer recorded in the same words, and refused, naming each, while a step it waits on is neither ticked nor done; `word` prints the commit a word was given for, or exits 1 when there is none, and a word is for one deploy: once its end is recorded, or the end of a newer deploy of the environment, one started after the word was given, there is none until the next approval, and that end closes the card, naming the newer deploy. `record` puts a deploy's start, each of its steps (the machine, the guests, the suite and its rows) and its end in the run record as it runs; its end closes the deploy's card with each step's outcome, or the step that failed and its log, and after them, where the deployer handed the end its failed step's own words of what the user does with `--does <words>`, those words as it wrote them; `--does` is taken on every record and kept on its entry. Every other operation, a command after a deploy, a restart, a check, is a `step`, recorded with its state, its doer, the agent it was handed to and its text, after the deploy it names with `--to` or on its own; one whose doer is the user, or an agent's marked `--held` for the user's word, waits as a rail row, `op/<env>/<n>`, until it is marked done or declined, but a user's step in the words of one the environment's open offer waits on, which crew records as one, `before` among its when words, and which is ticked on the deploy's card, with no row or card of its own while that offer is open, and `steps` gives each step's latest state as JSON. crew raises such a step's card in main-level ops's name, one at a time on an environment, each following the one before: the user's a `do` with the step's words and, from its text's `- why:`, `- where:`, `- command:` and `- done:` lines, why, where, each command whole and what is seen when it worked; a held one a choice of now, when the host is quiet, or skip. Recorded again while its own card is open, the step changes that card in place when its words, its doer or its hold differ, a change of doer between the user and an agent withdrawing the card and posting the new one following it, since Pending You changes no card's kind, and the command prints the line that adopts the card either way; only another step's open card holds a step's card back. It closes the card when the step is marked done or declined, and raises the next. A step an agent runs on its own has no card. `quiet` exits 0 when no Flume place of the drive works on the environment's host, as its runner there carries Flume's status, and no test of crew's runs there, and 1 saying what does.

Each drive has a main level in the session the teams file names: the **design agent** (elaboration on main and curation of signals), the **planner** (the only writer of bolts and placements, and the poster of the drive's review batches), the **reviewer** (started fresh for each batch, in a `review` tab, and ended once its summary is written) and the main-level **ops** (lands the bolts whose verification is green by one procedure, their submission to main through sluice in order, on the user's send on their kit's landings card, and deploys a kit with no deployer only on the user's word for that deploy), as tabs of the `<label>` workspace. The **operator**, `<label>-operator`, is the main level's fourth role and the drive's one door (record 0035): it works for the user, and every wait with no card is told to it. A main-level role runs in the main level's session unless its drive's `roles` names another of the machine's sessions for it, `roles.planner.session`, so a drive's design agent and planner can sit on two Claude accounts; `crew main up` opens a `<label>` workspace in each, and refuses while a role's agent still runs in a session it no longer stands in, which `crew main down` ends. The **console** is the `console` workspace of each host's operator session (the session named `<label>`), opened by `crew console up <label>` and closed by `crew console down <label>`, with no agent in it. It opens with a `shell` tab alone, a shell with crew on its path, and opens its `flow`, `rail` and `board` tabs only when they are named after the label, in any order, `crew console up <label> rail`; another word is refused, naming the three. The rail tab opens of itself too while no host job runs the host's follower, since its loop is then the follower. Every later `crew console up` keeps each tab already open, named or not, and a tab the user closed stays closed unless it is named again. `crew operator up <label>`, its name before record 0035, opens it too, with no tab named, and ends the operator agent a host's console held before, once it is not working, closing the panes crew recorded beside it. Each agent `crew main up` starts is greeted once it is up, marked `[crew]`: told to read where the drive stands and carry on with what is its role's; one that was already up is neither started nor greeted. `crew tell` prompts any of these agents by name, wherever it runs, marked with who sent it. Anything for another drive goes with `crew send <drive> "<text>"`, naming the drive by its label, to its operator, its one door, wherever it runs. The operator is told `[crew tell from <sender>] (sent to <drive>) <text>` and carries it on to the agent whose job it is, in the sender's words, and the send is one `send` entry in that drive's run record, with its length and never its text. Any other name, a team's from before teams left among them, is refused, naming the drives, and so is the operator's own send to its drive, which it carries on with `crew tell`; every brief says beside its roster that this is the one way. A tell to an agent waiting on a question in its pane fails with nothing typed, and says to send it again once the question is answered, whether herdr sees the question or crew's PreToolUse hook marked it when the agent opened a question or a plan for the user; the mark counts until the agent's transcript holds the answer. When herdr names no Claude session for the agent's pane, as after herdr's own restore resumed it, crew reads the session it recorded of that agent starting in that pane, and with neither, herdr's reading of the pane alone guards the tell. crew's greetings and notices go the same way. A greeting is read back: sent once the agent is ready, cleared and sent once more when its transcript does not show it, and when the second is not taken either, nothing is left typed, no greeting is recorded, and crew says the agent was not greeted, with the `crew tell` that would greet it.

A main-level role may instead **run as its kind**, one role at a time, on the user's word, by its drive's `runs` in the teams file, which names it on every drive: an object naming each of its five roles, `design`, `planner`, `reviewer`, `ops` and `operator`, `standing` while the role stands as above or `on-demand`, the host's runner having Flume run it in the drive's own stream, named by its label, while something is pending for it, and crew refuses a file whose drive lacks it, leaves a role out, names another key or gives a role anything else, or that names `flume`, the former key, whatever else it gives, naming the drive, the key and crew's own module, `services.crew`, `crew drive set`, or the machine's configuration that writes the file; with `standing` throughout, every role stands. A role that runs as its kind has no standing agent. crew carries five Flume kinds, `crew-design`, `crew-planner`, `crew-reviewer`, `crew-ops` and `crew-operator`, declared in `plugin/flume/kinds.toml`, so a host runs the kinds of the crew it pins, each one stage, `turn`, that lands nothing and ends at its report, with `plugin/flume/turn.md` its prompt; the host's runner launches a **run** of the role, the place `crew-<role>--<label>` cut in the drive's first blueprints repo, whenever something is pending for the role and no run of it stands, so a burst of events is one run and a role has one run at a time. Whatever names such a role is an **ask** of it, a record in `asks.rec` on the drive's branch, never words typed into a pane: a `crew tell` to it, crew's own notices among them, once crew reads that no standing agent of it is still up (one still up is typed into as before, and a tell herdr can't be read for is refused); a `crew send` to its operator; a capture landed through crew, of the design agent, one for each signal; a bolt's landing, of the planner and the design agent, and a landing that did not land, of ops with Flume's words; a change on a card in the run's name, which the host's follower hears from Pending You's notice, `pendingyou watch -- crew _answered`, while a drive whose main level is on the host runs a role as its kind, reading nothing of the card; `crew role open`; the batch `crew review` asks of the reviewer; and the batch `crew review delivered` hands back, of the planner. An ask is written in the commit of the act that makes it, once for its key where it has one, and its words stay in `asks.rec`, never in the run record. A place of a started bolt's work that waits on the role, stopped short asking it or waiting on its caller, is pending for it as an ask is, read from the runner's records, and the run answers it with `crew answer`. Those ends make no role wanted: they are taken by the next run something pending starts. A run is the role: its name is `<label>-<role>`, read from its place, and it has the role's rights over the plan, its cards and its entries. Its last act is `crew role end --report <path> "<what was done>"`, which ends the turn with those words and, in the same commit, asks the runners to confirm each end the turn took, one confirm in `requests.rec` for each launch, and writes the report that is its stage's deliverable, counting those ends, also when it took no turn; what came after its start stays pending for the next run, and a run lost before its end confirms nothing, so the next run takes its ends again. A run waits on nothing in its session: where its brief says to wait for an answer, a submission, a review or a tell, it ends its turn and the thing reaches its next run as an ask. Its work that lands is a place it launches, never a commit of its own: `crew role land <repo> <name> --brief-file <file>` appends to `requests.rec` a launch of Flume's chore kind named `<name>` in a repository the teams file or the plan names, on its default branch, in the drive's own stream, named by its label, on the main level's host, the file's text whole its brief and the run its recipient, which Flume builds and submits through sluice, its landing reaching the role's next run; a repository neither the teams file nor the plan names is refused. Ops runs nothing for a landing from its run: crew carries the user's send to the runner, and a landing that does not land comes back as an ask. The reviewer's run writes each batch's summary and runs `crew review delivered`, which records the batch, starts its reading session and raises its card in the planner's name as `crew review --wait` did, and asks the planner, naming the batch; `--wait` is refused for a reviewer that runs as its kind, and a batch whose summary is not written is refused by name. The user talks with a role with `crew role open <role> --label <label>`: an `open` ask, after which its run opens as the place `crew-<role>--<label>` in herdr on the main level's host and greets them in its pane, or, where the runner's records show a run of it live, nothing written and that run's place named to talk to now; refused where those records can't be read, and for a role that stands. `crew role start`, `end` and `land` are refused anywhere but a role's run, and `crew review delivered` anywhere but the reviewer's. For a role that runs as its kind `crew main up` opens no tab and starts and greets nothing, writes the role's record in `roles.rec`, from which the runner launches its run, and ends a standing agent of it still running once it is not working; a standing agent of it is ended at its next stop, told why, and never restarted, `crew revive` and `crew update` pass it over, `crew-role` refuses it, naming `crew role open`, and `crew main status` says it runs as its kind in its drive's stream, named by its label, whether a run stands and how many asks wait, the oldest since when.

`crew rail` lists everything that waits on the user, from any host, in four groups, always in this order: open proposals, review batches that still wait on the user, their card not yet answered and some unit of each neither landed, dropped from the plan nor held by a later batch, each kit with a bolt whose every unit has merged, one row naming each such bolt in the plan's order with what it waits on, main-level ops's, and operations: an environment's deploy offered and not yet approved, and an operation that is the user's to take (see Operations). Each row says what waits, when it began to wait and how long ago that was, and carries the commands that answer it, written to be pasted; within a group, the oldest comes first. A proposal waits from its entry in the run record (or the day it was opened), a batch from its review's end, and a bolt from its last merge. Each bolt's line on its kit's landing row says how the kit's landings card stands for it, read from the run record alone: carried by the open card, waiting on the user, naming the head the card shows when the bolt's head has moved since; held by the user's send, on the open card they answered or kept on a closed one, which main-level ops lands; or following, the next card under the kit's key carrying it, or the card after the one the user answered; a bolt that can't land and is no row of the card says nothing of it. Each bolt's line then ends with the bolt's age since its newest start and who held that time, by the same rule and from the same read as its head line on the board (see `crew board`), so the two never differ. Every row and every time is read from the plan, the proposals, the kits and the run record, and nothing is kept by hand: a row leaves the list as soon as its answer is recorded. A host that doesn't answer is named. A bolt whose every unit has merged is offered for landing only once every unit's latest change has been in a batch whose card the user has answered: until then its row names the units that have been in no batch and the batches whose card waits on the user's answer, and carries no command. Nor is it offered until its verification is green, which is the bolt's proof: its head, read where the bolt lives, is the commit at which one of its units, chores or fixes reads merged or landed, as the runner reports it, the record Flume holds for the runner after its tidy among them; sluice lands a piece only once the checks its policy requires pass, or beside its queue when none of them reads its changes, so a landing beside, a take-main fix's among them, reads green like any landing of its work. The host's **follower** keeps the list fresh, for every drive with an operator session on the host in one read: once a minute on its clock it fetches each repository it reads once, every drive's state branch, its runners' branches and blueprints main of that repository in one fetch; each second it looks at this host's caches, so a write on this host shows within seconds and another host's within the minute. It runs no sluice and reads no folder of sluice's: a submission's move reaches it in its runner's report, a move of the runner's branch at the clock's fetch, which puts the submission's number on its row at the refresh after. A rail or a board read more than three minutes ago is headed with how long ago, so a follower that has stopped is never taken for a live one, and a tab with nothing written yet says so, and that the host's follower writes it. A restart ends the tabs' commands, and herdr brings each tab's pane back as its shell alone: `crew console up <label>`, which swancloud's timer runs every five minutes, runs each tab's command again in a pane holding its shell alone, read from herdr's `pane process-info`, and leaves one running anything else, saying so.

When `crew card session batch/<n>` or `proposal/<n>` starts the reading anew because none runs, it changes the planner's open card in place to carry the link while the card waits on the user, and leaves a card the user has answered as it is, printing the link alone. `crew card end batch/<n>` ends the session by hand. A batch posted under `batch/<n>-<k>`, before a batch was one card, keeps a session for each unit it holds: `crew card session batch/<n>-<k> <unit>` starts one on that unit's change, given its Markdown files, proposal first, rather than its folder, on the host the teams file names for the unit's team; `crew card end` takes the unit the same way, `crew card end <key>` with no unit ends each of them, and so does the card's close. Each row of a landings card has one session too, its bolt's reading, on what the bolt brings to main: `crew card session land/<bolt>`, run on the host where the bolt's work ran and refused elsewhere, naming that host, writes the bolt's reading into `~/.local/state/crew/cards/<label>/land/<bolt>/<head>/` there, a page naming the bolt, its head and the units and chores that land, then each unit's change as the bolt holds it at its head, then the bolt's diff against main, from where it last met main to its head, less its change folders, as text, in as many files as keep each within the 2 MB plannotator opens in one file, each holding whole files' changes in git's order, a file whose own change passes that cut nowhere but named in its place and on the page with its size and where to read it whole, GitHub's compare view of that range and the `git diff` on the host where the bolt's work ran, and starts plannotator on those files as one review; it reads the bolt as its row does, and refuses a bolt that is no row that can land, saying why, and `land/<kit>`, which has no reading of its own. When a merge moves the bolt's head, crew ends the session on the old head and starts one on the new, and the card, changed in place, carries the new link; when `crew card session land/<bolt>` starts the session anew because none runs, as after the host restarts, or gives a running session's link again while the run record shows the kit's card standing without a row's reading, it has the kit's open card changed the same way while the card waits on the user, and leaves a card the user has answered as it is, printing the link alone. `crew card read land/<bolt>`, run by main-level ops on the bolt's host once crew tells it the reading was sent, gives what the user sent from the reading: annotations, word for word, as notes on the bolt's row, and an approval as landing nothing, since the user's send on the kit's card is the word to land; it leaves the card as it is and sets the decided session aside, so the next `crew card session land/<bolt>` starts it anew. With nothing sent it says the reading waits on the user, and with no session running it says so, naming `crew card session land/<bolt>`. The reading ends with the bolt's row, when the bolt lands and when a fix holds it, or by `crew card end land/<bolt>`; a card of the bolt's own from before, `land/<bolt>`, closed by the rail's sweep or otherwise, is no word on the row and ends not its reading.

The user reads a drive's constructed and amended changes in **batches** that span its bolts. A unit's change is due each time a construct of it delivers, and stops being due once a batch has held it at the commit that construct left. At each sweep of the rail on the drive's main-level host, crew counts the changes due from the run record and makes a batch due at the drive's setting in the teams file (`review`: `after_changes`, once that many changes are due, a whole number of at least 1, or `after_hours`, once that many hours have passed since its last batch with at least one due, a number above 0), or at once when a bolt has every unit merged and some unit's latest change outside a batch; it then tells the planner once (`batch.due`). The planner runs `crew review <label>`, which starts the reviewer, a main-level role greeted by nobody, fresh in a `review` tab of the `<label>` workspace on the main level's host, sent the changes due and how to read each at its commit (`review.start`). The batch is taken or sent again (`teams.15`): crew sends it once the reviewer accepts input, reads its transcript for it, and sends it once more when it is not there; taken at neither sending, the reviewer's input is cleared, the start is recorded refused and the command refuses, so no batch waits on a hand pressing Enter. A reviewer `crew review <label>` finds up but idle, its session holding no batch and no summary written since its last start, is ended (`review.end`) and the batch's reviewer started afresh, saying so, and `crew review <label> --wait` on it refuses, naming `crew review <label>`; one at work, at a question or that took its batch is refused as still reviewing (`teams.2`). The reviewer writes its summary to `~/.local/state/crew/<label>-main/reports/batch-<label>-<n>.md`, as prose with no code block, each unit's section opening with a paragraph of what it does and what the user would most care about, and nothing else; `crew review <label> --wait` returns its path once it is written, records the batch with each unit at its commit (`review.batch`), starts the batch's one reading session and raises its one card in the planner's name, keyed `batch/<n>`, however many units it holds, ends the reviewer and closes its tab: a notice titled by what its units' bolts are for, that says first how many changes there are to read and that nothing is to approve, names every unit with its bolt and its opening paragraph, asks nothing and links the session, filed in the kit of its first unit whose bolt crew can place. The batch's notes are the annotations the user sends from that session and the card's own note, which `crew card read batch/<n>` gives the planner: the planner hands each unit's on in the user's words, a note marked fix reaching the unit's bolt as a fix place, by the planner's `crew fix`. The user may also answer a batch in their own words in the planner's pane or the operator's, typed there or told from their shell: that agent runs `crew card answer batch/<n> --excerpt "<their words>"`, once for each batch, and crew records the batch answered only when it reads the words in that agent's own session transcript as the user's, never in what the agent wrote, another agent's tell, a tool's output, crew's own message or a word from the board (`batch.answer`, which keeps no words, only the transcript record they came from and their length). It counts as a tap on the card: the card held on that host is closed answered with the words, one held on another host is closed by the rail's sweep there, saying in whose pane and when, the planner's `crew card read batch/<n>` then says in whose pane, closing the card it holds, and the bolts the batch held are offered for landing. The words are the batch's notes: crew tells the planner them when the operator ran the command, and the planner sends them on as any notes. A batch answered already, on its card, in its session or in a pane, or one that waits on nothing, is refused. An unanswered card holds no code, but it holds the landing of each bolt whose unit's latest change it holds: a bolt is a row of its kit's landings card, and its rail line carries the word to land, only once each unit's latest change has been in a batch whose card the user has answered; and `crew bolt land` is refused while a unit's latest change has been in no batch. A batch whose reading session the user sent is answered too, its card's close the record, or crew's own close of it when no card closed: it counts as answered for a bolt's landing, and is no row, names no landing row and has no card raised for it until a newer card is posted under its key. A batch waits on nothing once each of its units has landed, has been dropped from the plan since the batch was made, by `crew unit drop`, a proposal's drop or its bolt's drop without `--requeue`, or is held by a later batch, whose card then carries that unit to the user, as when the user answered it in the planner's pane: crew reads such a batch closed from the run record alone, on every read of the rail and the board, so it is no row, `crew review --wait` raises no card for it and the rail's sweep posts none; the sweep on the main level's host records crew's close of it once, in the planner's name, saying which units have landed, which were dropped and which later batch holds the others (`batch.close`), before it asks anything of Pending You, and withdraws a card still open under its key with the same words. A batch with one unit that has not landed, was not dropped since and that no later batch holds stays a row until the user answers its card. crew's close is not the user's answer: a bolt still lands only once each unit's latest change has been in a batch whose card the user has answered.

A drive or host without Pending You keeps the rail as it is, and its main level's agents tell the drive's operator of every wait instead.

A herdr server that restarts resumes each agent in its saved pane folder, which is the folder crew moved the pane to before starting the agent, since Claude finds a conversation only from the folder it began in. crew's SessionStart hook gives a resumed agent its name and identity back, and at each compaction its brief, which such a session keeps only until its first. A main level's design agent, planner, ops, operator or reviewer gets them back only on the host the teams file names for its main level, and `crew-role` starts one only there: a pane herdr replays on any other host, a standby that once ran the main level, gets no identity, pane name or brief, and is told at each start that it is no agent of crew's there and which host the main level runs on. An agent that never had a message has no conversation to resume, and its pane comes back as a shell, so crew gives every agent it starts a first message: the reviewer its batch, and every other agent a greeting. `crew revive`, run on a host after a restart, brings back each main level's standing agent of that host whose pane came back empty, from its last conversation or fresh, greets each it brought back, and leaves a main level taken down with `crew main down` as it is. A pane whose folder was gone when herdr's server started, as a worktree removed since, comes back dead, listed with no terminal behind it: `crew main up`, `crew console up` and `crew revive` close it and open it again in its workspace, saying so, `crew revive` then picking up its agent there, and never touch a pane an agent holds. `crew sites` lists each host's bolts, units and fixes with the URL of each running dev server, named by swancloud's `devurl` and found among the host's portless routes.

### Holding a host, and updates

`crew hold <host>|--all "<why>"` puts on the brakes before herdr is upgraded or a host rebooted. crew starts no agent on a held host until `crew go`, and refuses every command that would, saying who held it and why. `--all` holds every main level's host. Every standing agent up there, a main level's, is told to finish the step it is in and start nothing new. `crew hold status` says what still works on each host: an agent working, one waiting on a question to you, one running background work of its own, crew's tests. `crew hold wait` waits until each host is quiet and then ends every crew agent there, keeping its panes, so herdr's restart brings back only shells; `--now` ends them at once. `crew go` lifts the hold, brings each standing agent back with its conversation through crew, greeted, tells one still up to carry on, and runs each console's tabs again.

crew's commands run the crew the host has installed, and so does every command crew hands on for a later run: each brief's commands, a command forwarded to this host, a restart's hand to `crew _renew`, the follower's Pending You notice, its update and its start again, and the console's tabs. A command crew runs on another host, a tell, a send, an ops act or a command forwarded to a main level's host, is likewise the crew that host installed: `crew` by its name, as the host's login path finds it, run over ssh to the host's `ssh` name in the teams file's `hosts` as the one asking, its `CREW_AGENT`, `CREW_LABEL` and `CREW_SESSION` carried. crew looks for no checkout of itself there, and a host whose login path finds no `crew` fails, saying that host has no crew on its login path, with nothing run there and no other crew tried. The installed crew is a checkout's own `plugin/bin/crew` where crew runs from a checkout; where it runs from a build, the first `crew` on its path in a folder outside the Nix store, a profile's link that each install moves; and the build's own `plugin/bin/crew` only where it finds neither. So crew's code is live on every call, but an agent takes its brief and crew's plugin (its hooks, skills and this band) once, at its start, and its hooks run from the plugin folder its session loaded. Each start records the crew it loaded, and what it was started with. A checkout's commit and version are read from git, its version the newest release tag whose source is HEAD or before it, the source being the commit the tag's release commit was cut from, with `+<n>` for the commits past that source. A build's are read from `plugin/release.json`, which crew's tree holds at `0.0.0` on main and at the release's version at its tag, a build adding the commit it knows: its version `v<x.y.z>` for a release's, and otherwise the version and the commit's first seven characters, `0-unstable-2026-11-08+fcedc22`, main's `0.0.0` never shown as a release's. A copy of a tag's `plugin/` with nothing added reads as its version, `v<x.y.z>`, with no commit. `crew _release` prints what a crew is, as one line of JSON, the commit null where a release names none, which is how one crew reads another. `crew _found <agent>` is how one crew asks another to find an agent: where herdr names an agent in no pane on its host, that host's crew looks for it in the pane crew keeps for it, gives its name back, and answers in one line of JSON, as a tell from another host asks it. A standing agent is due a restart when its brief, model, effort or folders changed; when the installed crew is a checkout and the part of crew's plugin a session loads changed since its start's commit; and when the installed crew is a build of another release than its start recorded, since its session loaded that build's folder whole. A start from a build with no release file records none, so an install makes such an agent due only when its brief changes, `crew main down` and `crew main up` restarting it on the installed crew; and where crew can't read the installed crew it makes no agent due for its plugin and says why. crew restarts a due agent at its next stop, once its turn has ended with no question open and nothing of its own running in the background but crew's waits. Every standing role resumes its conversation and is told what changed. crew's Stop hook catches an agent at the end of its turn, judging it against the installed crew whichever build the hook runs from, the host's follower catches one sitting idle when crew's checkout, the installed crew or the teams file moves, and `crew update` does it by hand. Nothing restarts on a held host. Each agent's band shows the crew it started on, and once it is due the version of the installed crew it takes at its next stop.

## Seeing what happened

```
crew events [--label L] [--about <object>] [--since <time>] [--follow] [--json]
crew events --push [--label L]
crew trace  <object>
crew page   <label> [--out <file>] [--since <time>]
crew page   --fleet [--out <file>]
```

Every crew command that moves work appends one entry per act, after the act, to the **run record** of the drive it acts for, on the host where it ran: `~/.local/state/crew/<label>/runs/<host>/<YYYY-MM-DD>.rec`, one recutils file per UTC day, each entry one write, never rewritten. An entry holds:

- `Id`, `At` (UTC) and `Host`, where crew ran;
- `By`, the agent crew started that asked (`CREW_AGENT`), or `<user>@<host>`, and `Session`, that agent's Claude session as `<host>:<id>`, carried with a command crew runs again on another host;
- `Act`, such as `unit.add`, `bolt.start`, `tell` or `agent.restart`; `forecast`, a started bolt forecast on its kit's landings card to conflict with main; `batch.due`, `review.start`, `review.batch` and `batch.close`, a drive's review batches and crew's close of one that waits on nothing; the card acts, `card.post`, `card.update` and `card.close`, which crew's hook writes for an agent's card and crew for its own, and `card.reading`, a try of a batch's, a long proposal's or a landing's reading after its card was raised, done or refused; `stage.answer`, `crew answer`'s retry of a Flume place; `kit.rename`, a repository's records renamed, on `kit/<new>` from `kit/<old>`, with `Repo` and `Count`, through which no reader maps a name; `ask`, an ask of a role that runs as its kind, on its run and the record it names, `turn.begin` and `turn.end`, a run's start and end, and `role.land`, a run's launch of work that lands, on `role/<role>/<name>` and the run; and, in entries from before, acts crew writes no more and `crew trace` still prints as written: `bolt.give`, which handed a bolt to a team, `stage.start` and `stage.end`, a stage crew drove in a slot, and `slot.free`, `team.up` and a team's other acts, `team.cross`, a team's crossing to Flume, its `State` the stream its work ran in, `plan.agree`, a conductor agreeing to a proposal, and `amendment`, `unit.rebase` and a unit's `forecast`, what reached a unit from another;
- `On`, each object acted on, and `From`, each object it came from, as typed names: `unit/<unit>`, `chore/<chore>`, `bolt/<bolt>`, `queue/<kit>`, `signals/<id>`, `agent/<name>`, `fix/<bolt>/<name>`, `fix/main/<kit>/<name>`, `role/<role>/<name>`, `batch/<n>`, and, in entries from before, `team/<team>`, `stage/<unit or chore>/<stage>` and `stage/<bolt>/proof`;
- `Commit`, `<owner>/<name>@<sha>`, when the act wrote one, and `Why`, the subject crew composed from the names of things;
- `Refused`, crew's reason, when a command that would have moved work was refused;
- a tell's and an ask's `Chars`, a `turn.begin`'s `Took`, how many asks and waiting places it took; a bolt's forecast's `Heads` (`bolt/<bolt>@<sha> main@<sha>`), its conflicting `Paths` and `Reached`, `held` or `left` as the user left the bolt; in an entry from before, a stage's end's `Result`, `Tasks`, `Head`, `Ended` and `Delivered`, `Observed`, a construct's `Amended` and `Took`, a unit's forecast's `Heads`, `Paths`, `Reached` and a stage start's `Forecast`, and on an older crew's own `unit.after`, `After`, `Lifted` and `Settle`, each read as written; a review batch's `Batch` and `Units` (each `<unit>:<bolt>@<commit>`), and a batch due's `Count`; and a card act's `Card` (the Pending You card's id), `Key` (its rail row's card key, or its record key) and `Unread` (why its reading could not open, crew's own message, on the post or change of a card raised without it), on the row's object, on `record/<kit>/<number>` for a decision record's card, or on `agent/<name>` for a card with neither key.

No entry holds text anyone typed: not a tell's text, an answer's words, an intent, a goal, a reason or an excerpt. A read writes nothing, and a record that can't be written is said on standard error and changes nothing about the command. `recsel -t Entry` reads the files with no crew involved.

Every entry reaches the drive's branch as it is written. An act that writes the branch carries its entry in its own commit (see State), and once that push is accepted the host's own file holds it too. An act that writes no branch, a tell, a send, a launch or a card's post, and an act refused before its write, pushes its entry to `runs/<host>/<YYYY-MM-DD>.rec` there before it goes on, as a commit of its own from that host, by the one write every state write takes, its subject `runs(<host>): <act> <first object> (<agent>)` and its `Crew-Entry:` trailer naming it. Each day's file on the branch is the union by `Id` of what it had and what the host has, so a host only ever adds to its own files, and one that is asleep or rebuilt loses nothing it pushed. When the push can't be made, GitHub out of reach, the branch not started or a file of the host's failing `recfix --check`, the command says so once on standard error and does what it would have done; the entry waits in the host's file, and the host's next entry or write pushes it, each still a commit of its own, a write's after its own commit. `crew events --push` pushes by hand what a refused push left, or says nothing is left. `crew events` reads the run record from the drive's branch alone and prints it in time order, asking no host for it, so a host that is asleep hides nothing it pushed; it names the branch when that can't be read. `--follow` reads the branch as this host's cache holds it, again whenever its tip moves, reading only the files that changed, and prints each entry once it is there: a write on this host moves the cache at once, and the branch is fetched once a minute, by the host's follower, or by the follow itself for a drive no follower on the host follows, so another host's entry shows within the minute. The console's `flow` tab runs it. `crew trace <object>` prints one bolt's, unit's, chore's or signal's history from the entries alone, and `crew trace agent/<label>-<role>` a role's asks and turns: what was done, by whom, with which commit, what it came from and what came from it, each line with the `zoe <session>` to open on its host. A bare name is tried as a unit, then a chore, then a bolt, then a signal; `report/<file>` and `proof/<file>` find the end that delivered them. crew writes no stage's start or end and frees no slot: a stage's start and end are Flume's, read from the runner's records, and the `stage.start`, `stage.end` and `slot.free` entries an older crew wrote are read and printed as written.

`crew page <label>` writes the drive's page, one HTML file that opens on its board: the four lanes `crew board` reads, Inception, Bolt plan, Construction and Operation, made by the same read at the same commit of `<label>/main` as the rest of the page, and drawn as the Boomdrive mockup's phases view draws them: a signal as a quote under who captured it, a proposal as a sheet, a queued unit as a slip, a bolt as a ledger with its units as a chain, a started bolt's headed by the host and stream its work runs in and naming no team or slot, a landed bolt as a record with when, by whom and its units, and every rail row a ✓ marker on its object, saying whether its card is open and who asked it, or that it has no card, its post refused, Pending You's words shown when the marker is pointed at. The lanes sit side by side on a desktop and stack under 760 px, as on a phone, and the page follows the viewer's light or dark preference. A strip under the header shows each host the board asked, one that did not answer marked, and what needs attention. A click on any item of the board, or Enter on it, opens its dock: one panel over the right of the board, which does not move under it, its head in the item's form, holding the item's details as the page's data and lineage hold them, its markers in the board's own words, each item it names that the page draws a link that opens that item's dock in its place, with a back control along the way it came, and its history from the run record as `crew trace` walks it. No team has a dock. The Claude account a session of the main level runs on has a dock listing the drive's main-level agents on it with their host and session, opened from the fleet page's subscription; a deploy opens the same dock from the Operation lane and from the deploys view. Esc, the dock's × or a click outside closes it, and under 760 px it fills the screen with its back control. The dock open is kept in the page's address (`#dock=<key>`), so a reload, or a page written over this one, opens it again, and none is opened for an item the page no longer holds. The view shown is kept in the page's address (`#view=<view>`) and in the browser for that drive, so it survives a reload and a page written over this one. The header names every drive in the teams file, and each other one links to its page in the layout of this page's own file: `../<label>/page.html` in crew's, `~/.local/state/crew/<label>/page.html` or the same under another folder; `<label>.html` beside a page written as `<label>.html`, as swancloud's board serves the pages side by side; `../<label>/<label>.html` when both the file and its folder are named for the drive; and none, which the command says, for a page whose file and folder are not named for it, since crew cannot tell where the others are. Before the drives the header links to the fleet page in the same layout: `../page.html` from crew's `<label>/page.html`, `index.html` beside a page written as `<label>.html`, and none in any other. Each dock ends with a one-line field for a word to the item's agent, saying whom it goes to: for a bolt, a unit or chore, a fix or a proposal, the drive's planner; for a signal, the design agent; for a landing, a deploy or an operation, main-level ops; and for a subscription, the operator. Send posts the word to the page's own address, `word` beside it, where swancloud's listener on the board's host hands it to `crew tell --board`, and the dock says what came back: `sent to <agent>`, the field emptied, or crew's words for why nothing was sent, the word left in the field; when the listener does not answer, that nothing was sent; and a page opened from disk sends nothing. The board and its docks answer nothing: a dock has no control that answers or moves anything, a word from it answers no card, and its card is answered on the rail. Making the page asks every host of the drive for its kits, as `crew board` does.

`crew page --fleet` writes the fleet page, every drive of the teams file at once, made from the one read `crew board` makes of all of them, one file that loads nothing, in the drive page's colours, light or dark as the viewer prefers, its drives side by side on a desktop and stacked under 760 px. Each drive is a block saying the commit of its plan it was read at, and holding: where it runs, each host the board asked for it, its main level's and its runners', one that did not answer marked, and its main level's host, and under each host the herdr sessions its agents run in, each naming its design agent, planner, ops and operator there, with the Claude account the drive's `accounts` gives the roles in it, crew showing only the sessions its roles run in; its kits, the repositories its plan and its landings name, each with its main's last landing in the run record's window of seven days (the bolt, the commit main then held, when and who landed it, or none since the window's start) and what is queued for that main, the bolts that wait to land with their landing card open or none, those in construction, and how many bolts are planned and units queued; and what needs attention, in the board's words, with how many of its cards are open. Above the drives the page shows each Claude subscription, every account a drive's `accounts` gives a role and every account a host published a reading for, by name: its five-hour and seven-day use, each the percentage used and when it resets, and its weekly use by model where the reading gives it (Opus, Sonnet, and each model the server names, such as Fable), exactly as the host holding its sign-in published them, a figure the reading leaves out said not given, each in words and a plain bar, never graded, summed or coloured by level; which host read it and how long before the page was made, and every other host's reading with its age or its own words for why it could not read, a subscription with no reading made saying its use could not be read and one no host published for saying so; and beside its use, computed from nothing of it, the sessions on it by host, each with crew's agents in it on that account, and the drives whose agents run on it, each opening its page at this subscription's dock. Each drive's name links to its page, and each drive on a subscription to its page at the subscription's dock, in the layout of the fleet page's own file: `<label>/page.html` beside it written as `page.html`, crew's own, by default `~/.local/state/crew/page.html` beside the drives' folders; `<label>.html` beside it written as `index.html` with `--out`, as swancloud's board serves the pages; and none, which the command says, for any other name. The command prints the path, then as of when and which commit of each drive's plan, then each host or plan that did not answer, by drive, then each published file whose use it could not read, with why, and that no subscription's use is published when the folder holds no file, and writes the page all the same; like the board, it answers nothing.

The page's flow view, one switch away, draws the drive's lineage: its signals, agenda items, proposals, units and bolts as columns in that order, a line from each to what it led to, a timeline of the entries per day beneath, and each object opening to its history, the entries `crew trace` prints for it, each with who did it, on which host, with which commit, and the `zoe <session>` to open. Selecting an object marks everything it came from and everything that came from it; a filter hides closed and landed work, and a box narrows by name. Which objects there are, how they are linked and in what order things happened are read from the run record alone, by the walk `crew trace` makes, so the page and the trace cannot disagree; labels and present status (a signal's assertion and move, an item's subject, a proposal's case, a unit's intent and stage, a bolt's goal and the host its work runs on) are read from the drive's branch at the commit the entries were read at, and an object the branch no longer holds, such as a landed bolt's units, is labelled from its newest entry. The file holds its data, style and script and loads nothing, so it opens from disk with the network off; the one request it makes is a dock's word, posted to its own address when the user sends it. It is written whole to `~/.local/state/crew/<label>/page.html` on the host where the command runs, or to `--out`, and never committed; the command prints its path, then as of when and which commit of `<label>/main` it was drawn from, then each host whose kits did not answer, whose units' and bolts' stages the page leaves blank; its run record is the branch's, whole. `--since` draws only the entries from then on. When the branch can't be read, no page is written and an earlier one is left as it was. The page's deploys view, a third switch, draws each environment's deploys as a timeline over the same window, oldest at the top, so the sequence of what was approved, replaced or left waiting reads down it: each deploy with the commit it moved from and to, the user's word on it as its card's answer recorded it, its steps, the suite's checks and its outcome, the bolts it carried, each with the proposals the lineage joins to it, which say what the deploy brought, and the after-deploy steps of its commit with their doers and states, then the operations waiting on the environment; it is read from the ops entries of the main level's host and the landings, as the board's Operation lane is. Nothing reads the page and making it appends no entry: it is a view, made again to refresh it. The operator agent makes it and opens it beside its pane when asked to show how work flowed.

## The flake

crew's flake, `flake.nix` with the rest of it under `nix/`, gives a host crew and writes its teams file, so a host configures crew through its own configuration alone, with the Boomdrive flake, which takes it as a locked input and re-exports its module, or without it (agentplot/boomdrive record 0023; record 0058, `flake.1` to `flake.3`):

- `packages.<system>.crew`, also `default`, for `aarch64-darwin`, `aarch64-linux` and `x86_64-linux`: the tree's `plugin/`, and `bin/crew`, which runs the plugin's own `bin/crew` with jq, Python 3.13 and recutils first on its path; git, herdr, wt and openspec stay the host's. Its version is the one the tree's `plugin/release.json` gives: a release's `x.y.z` at its tag, and `0-unstable-<date>`, of the tree's last change, for main's `0.0.0`; any other version fails evaluation, naming the file. The package holds the tree's `plugin/release.json`, which crew reads where it runs from the build; where the flake knows the commit it is built from, it writes that commit and the package's version over it and gives them as `release`; built from a tree with uncommitted changes, it writes nothing, holding the tree's file, and `release` is null.
- `darwinModules.default` and `nixosModules.default`, each also `crew`, declaring `services.crew`, each keyed `github:agentplot/crew#<platform>Modules.crew` as Flume's are, so a host that imports it directly and through the Boomdrive flake's module declares `services.crew` once, the first revision imported winning:
  - `settings`, the teams file, each key named as the file names it: `drives`, every drive by its label, `services.crew.settings.drives.<label>`, each with its `blueprints`, `state`, `machine`, `session`, `folder`, `repos`, `accounts`, `review` (`after_changes` and `after_hours`), `runs` and, where given, `roles`, each option's description saying what it holds, its unit and its range, none with a default and no `partition` among them, its `label` its name, which no host sets; `hosts`, each host by its name with exactly its `ssh` name and its `kind`, `darwin` or `nixos`, with no default; `consoles`, where the host opens any, each drive's label with the absolute folder its console opens in, unset by default and then no key of the file; and `version`, crew's own, read from `plugin/lib/crew.py`, which no host sets. The file is the settings as compact JSON with every unset key left out, its drives listed in the order of their labels, each with its `label`: the bytes swancloud's writer gives for the same drives in that order. Another module, as agentplot/boomdrive record 0032 has the Boomdrive flake's give them from its accounts, can give a drive its `machine` and `state` by its label, while the host's settings keep the drive's other keys. Each of the two is written once: a second writing, even of the same value, fails evaluation, naming each place that writes it. Evaluation fails for a drive that lacks a key crew requires, a drive another module gives and the host's settings do not configure among them, drives given as a list, a drive's name crew does not accept, a `label` the host sets, no drive, a `runs` that leaves out a role, names another or gives one neither `standing` nor `on-demand`, a `review` that lacks `after_changes` or `after_hours` or names another key, `every` and `hours` among them, an `after_changes` that is no whole number of at least 1 or an `after_hours` that is no number above 0, a `folder` that is not absolute, a `repos` entry that is no `<owner>/<name>`, an `accounts` that leaves out a role, names another or gives a name crew does not accept, no `hosts`, a host's name crew does not accept, an entry that lacks `ssh` or `kind` or gives another key, a `kind` that is neither, a console's folder that is not absolute, and a `teams` key. Which keys agree with which, a machine with no host, a blueprints repo not kept, two accounts in one session, is crew's to judge at load.
  - `host`, this host as `hostname -s` names it, the name the drives' `machine` gives a host. It is no key of the file, since crew reads its host from `hostname -s`; the activation says when this host's name is not it.
  - `package`, the crew installed in the system profile: the flake's for the host's system unless the host gives its own, laid out the same.
  - `user`, on NixOS, the user who runs crew; on nix-darwin that is the primary user, who must have a home.
- The system's activation links `~/.config/crew/teams.json` to the module's file as that user: a link there is replaced, and a file there that is no link is moved once to `teams.json.before-nix`, the link refused while that path is taken. The module writes nothing else and runs no service: no file under `/etc`, no launchd job or systemd unit, and crew reads no file of the fleet's.

The flake's checks are the moon project `nix` (`nix/moon.yml`): `format` (nixfmt), `lint` (statix and deadnix), `typecheck` (every package evaluates, and each module in a system of its platform) and `test` (the module's file held byte for byte to `nix/tests/files/deneb.json`, which crew's logic tier loads as its teams file, each module's activation and assertions, each module imported twice, and the link's own cases), each tagged `check-full`, so `tests/suite` and sluice run them beside the suite. They evaluate the flake offline and read-only against no store, building nothing, reading the inputs crew's devenv shell fetched from `CREW_FLAKE_INPUTS`.

## Needs

`herdr`, `jq`, `python3`, `git`, and `recutils` for the plan; in each kit `sluice`, which crew runs only for a preview, and `openspec`; `devurl` and `portless` for `crew sites`. crew's own toolchain is devenv's system tools, `jq`, `recutils`, `proto` and `git-cliff`, with convco for the commit-msg hook entering the shell installs, and the application tools `.prototools` pins, which entering the shell installs when one is missing, and activates: `moon`, and Python at the minor every host runs crew on, with `uv`; the tiers' `venv` task syncs pytest from `tests/uv.lock` into `tests/.venv` before every run of them, with the uv moon's toolchain gives, since moon's own install is skipped under `--force`, as sluice runs.

CI releases crew on each push to main that git-cliff finds a new version in (`.github/workflows/release.yml`, `cliff.toml`). A release's tag, `v<x.y.z>`, names a release commit cut from the pushed commit, in which `set-version.sh` writes the release's version into `plugin/release.json` and crew's manifest, `plugin/.claude-plugin/plugin.json`, both `0.0.0` on main; nothing is committed to main, and the tag alone is pushed. So a build of the tag, or a copy of its `plugin/`, reports the tag's version with nothing added. `devenv shell -- release-preview` shows the version and notes the next push to main would release.

`tests/run [name...]` runs crew's tests one after another on stub `herdr`, `ssh`, `claude` and `wt submit`, each simulated host with its own scratch home, so no test reaches a real session, host or agent. `tests/suite` runs them as moon tasks, one per test file, each running its test through `tests/run`, side by side, beside every other project's `check-full` tasks, the flake's checks of the project `nix` among them, each named `<project>:<task>`, as `tests/suite nix:test` runs one; a test whose inputs are identical to a run that passed on the host, in any worktree of crew, is replayed rather than run again. `tests/suite --affected` runs only the tests a change affects, against the merge-base with `main` and counting uncommitted edits, `tests/suite <name>...` the ones named, and `tests/suite --force` runs without replaying. An agent runs the tests that prove what it changes by name while it works and `--affected` once before its merge, never the whole suite by hand: sluice runs every `check-full` task afresh on each submission to a bolt and to main, as crew's `.config/sluice.toml` requires. Every test waits for one of the host's test slots (`tests/slot`), as many as its cores less two hold at what one test costs the host beside others, a core and a half, unless `CREW_TEST_SLOTS` says otherwise, shared by every worktree on the host, and holds it only while it runs: whatever a test leaves running, a board follower a failing test never ended among them, holds no slot and is ended with it, passed or failed. The tasks are `tests/moon.yml`, written by `tests/moon-tasks` from the test files with each task's inputs: crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import) and the common files, and whatever else the test's outcome depends on, named on a `# Reads:` line of its opening comment; after adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`, since `tests/suite` refuses to run while they are out of step. Both run in crew's devenv shell, and enter it themselves when started outside it; crew's other tools run through it per command, `devenv shell -- <command>`, and a terminal enters it with `devenv shell`, or direnv with the checkout's `.envrc`. crew's mod has its own cases, `plugin/tests/*.test.ts`, run as the task `mod` by `tests/mod`, which runs them with `claude plugin test plugin`: Claude Code's test kit, with no session, model, sign-in or network. `claude plugin test` takes no option before `plugin`, so where `claude` is a wrapper that adds its own, `tests/mod` runs the program the wrapper's last `exec` names, once it answers `--version` as Claude Code; `CREW_TEST_CLAUDE` names another. A live test, `tests/t-<name>-live.sh`, reaching a real service, is no task: `CREW_TEST_LIVE=1 tests/run <name>-live` runs it.
