# Design: crew publishes a flake whose module writes its host file

## Context

agentplot/boomdrive record 0023 (accepted by the user 2026-11-06) has the Boomdrive flake configure a whole host, each tool by its own module, which the tool's own flake publishes and the Boomdrive flake takes as a locked input and re-exports. Each module writes its own tool's file, each key named as the file names it, and no module writes another tool's file. For crew: "`services.crew.settings.partitions` lists every partition with its `machine`, and `services.crew.host` names this host to crew. Where the control plane is crew and no `[control_plane.crew]` is written, the Boomdrive module writes it: the host from `services.crew.host`, and each partition whose `machine` is this host. [...] neither the runner nor crew changes." Its consequences: "afterthought/crew a flake with its package and a module for its host file", and swancloud, once the modules land, "passes deneb's facts as option values and stops writing Flume's, sluice's and crew's files". The talk's sketch of deneb (boomdrive `design/the-flakes-configuration/deneb.nix`, on `origin/design/the-flake-configures-the-whole-host`) sets `services.crew.host = "deneb"` and `services.crew.settings.partitions` as a list. agentplot/blueprints' principle 10: a tool's file is written by its own module, by hand or by a control plane's local layer, and never by another tool.

Today crew publishes no flake. swancloud packages crew (`packages/crew`: the commit's `plugin/` copied under `$out/plugin`, two pins, chosen per host by `lib/host-crew.nix`), puts `crew` on the user's path by its own wrapper (`lib/claude-account-tools.nix`, `crewCommand`), and writes `~/.config/crew/teams.json` through home-manager from `lib/herdr-published.nix` `teamsJsonFor`, which is `builtins.toJSON` of `{ version; partitions = [ { label; partition; blueprints; state; machine; session; review; roles?; flume } ... ]; }`. deneb's file, read 2026-11-07, is that compact JSON with no newline at its end, a link into home-manager's files. crew reads it in `crew.load` (`code.5`): version 5 alone, every partition's keys checked against the hosts file, which swancloud also writes, `~/.config/swancloud/herdr-hosts.json`. crew reads its own host's name as `hostname -s` (`crew.this_host`, `plugin/bin/crew` `this_host`).

Boomdrive's flake is the family's shape for this (boomdrive `flake.nix`, `nix/modules/options.nix`, `darwin.nix`, `nixos.nix`, `toml.nix`, `activate.sh`, `nix/tests/`, `nix/check.sh`, `nix/moon.yml`, at `3f428cf`): settings rendered at evaluation, so a check compares the text without building; nix-darwin's module in the primary user's login, NixOS's for a named user; the file linked at the tool's own path by the activation, a file there moved aside once; and the checks a moon project `nix` that evaluates offline and read-only against a dummy store, the inputs fetched by the devenv shell (boomdrive record 0020, its design Decision 14). Flume and sluice have not yet published their modules (their units are planned beside this one), so this module matches Boomdrive's.

Rules this design relies on: `code.5` (crew reads the teams file and never writes it, and no field has a default: the command still writes nothing, and the module, which is the machine's configuration, gives no default either), `code.4` (a label, a machine and the host are names), `code.1` (crew's Python imports nothing new; the devenv's tools, amended), `state.4` (crew runs no service; the module adds none), `read.1` (a mismatch the activation can see is said, never guessed past), `roles.5` (the module holds no mechanism of Flume's, sluice's, Timber's or Pending You's: it writes crew's own file, which the family's record gives crew), `tests.5`, `tests.7`, `tests.10` and `tests.11` (the checks run as moon tasks tagged `check-full` through the shell, with inputs that are what their outcome depends on, and reach no other host). Pages whose areas it touches: `tests.md` (`tests/suite`, `tests/t-suite.sh`, `tests/moon-tasks`, `devenv.nix`, `.moon/`), `docs.md` (README, `openspec/config.yaml`), and the new `flake.md` (`flake.nix`, `flake.lock`, `nix/`). It amends `code.1` and `tests.5` and adds `flake.1` to `flake.3`.

Departures: from principle 10's file names and layers, crew's file keeps its name, `teams.json`, and has no local layer, since record 0023 changes nothing crew reads and a drive's own control plane replaces crew (`roles.9`); from `tests.11`'s three tiers, the flake's checks are a fourth kind beside them, the checks of the flake's own project, which test no decision of crew's command (`flake.3`).

## Goals / Non-Goals

**Goals:** a host configures crew through `services.crew` alone, on nix-darwin or NixOS, with or without Boomdrive; the module writes the same bytes the fleet writes today for the same partitions, so a host moving to it changes no byte crew reads; the Boomdrive flake can re-export the module and read `services.crew.settings.partitions` and `services.crew.host`; crew's gate checks the flake on every change that touches it.

**Non-Goals:** the Boomdrive module's derivation of the runner's crew table (boomdrive's `crews-partitions-give-the-runner-its-crew-table`); swancloud's move to the module; the hosts file, which crew still reads and the fleet still writes; any change to what crew reads, its version or its commands; a binary cache for crew, which builds nothing to cache; anything on crew's main.

## Decisions

### Decision 1: the flake, its systems and its package

`flake.nix` at crew's root, the rest of the flake under `nix/`, as Boomdrive's. Inputs: `nixpkgs` (`github:NixOS/nixpkgs/nixos-unstable`, Boomdrive's, so a host's `follows` lines them up) and `nix-darwin` (`github:nix-darwin/nix-darwin`, its `nixpkgs` following), the tests' nix-darwin, which a host's configuration follows to its own. Systems: `aarch64-darwin`, `aarch64-linux`, `x86_64-linux`, Boomdrive's, since nixpkgs refuses `x86_64-darwin`.

`packages.<system>.crew`, also `default`: crew is bash and Python the host runs, so nothing compiles. The derivation copies the tree's `plugin/` (a fileset of that folder alone, so a change elsewhere in the tree moves no path) to `$out/plugin`, unpatched (`dontFixup`), as the fleet's does, and writes `$out/bin/crew`, a script that puts jq, Python 3.13 (the hosts' minor, `code.1`) and recutils (`recfix`, `state.1`) first on its path and runs `$out/plugin/bin/crew`. A wrapper, never a link: `plugin/bin/crew` finds its root from its own path unresolved (`here=$(cd "$(dirname "$0")" && pwd)`). git, herdr, wt and openspec stay the host's, as crew's `openspec/config.yaml` says. Its version is `0-unstable-<date>` from the flake's `lastModifiedDate`, nixpkgs' form for an untagged commit; crew keeps its version in no file (`code.10`) and reports its own from git. Not taken: an install check like the fleet's, which proves a fetched pin is whole: the flake builds its own tree, which crew's own suite already checks.

### Decision 2: `services.crew`'s options, named as the file names them

- `enable`.
- `package`: the flake's crew for the host's system by default; a host's own is any package laid out the same (`plugin/`, `bin/crew`), as the fleet's will be.
- `host`: a name (`code.4`), no default: this host as `hostname -s` names it (Decision 5).
- `settings`: crew's teams file. A submodule whose free-form type is JSON's, so a key the module does not declare passes to the file and crew judges it (RFC 42, as Boomdrive's). Declared:
  - `version`: read-only, the version `plugin/lib/crew.py` reads, taken at evaluation from its line `VERSION = <n>`, evaluation failing, naming the file, where there is none. One source, so the module and the crew of the same commit never name two versions.
  - `partitions`: a non-empty list, each a submodule, free-form JSON, declaring what `crew.load` requires with no default (`code.5`): `label` and `machine` (names), `partition` and `session` (non-empty strings), `blueprints` (a non-empty list of `owner/name`), `state` (`owner/name`), `review` (`every`, a positive whole number; `hours`, a positive number) and `flume` (`design`, `planner`, `reviewer`, `ops` and `operator`, each `false` or a name, and no other key); and `roles`, optional, its keys `design`, `planner`, `main-ops`, `operator` and `reviewer`, each optional, giving `model`, `effort` (one of crew's levels) or `session`.
- `user`, NixOS only: the user who runs crew (Decision 4).

Two assertions the types cannot make: no label listed twice, naming it; no `teams` key, which version 5 has no place for. crew's load still checks everything at its read (`code.5`, `read.1`); the module refuses at evaluation what it can see. Not taken: defaults for `flume` (every role `false`) and `review`, the fleet's values, which would make the module a second place a default of crew's file lives, against `code.5`; a list of partitions keyed by label as an attribute set, which would reorder the fleet's list and break Decision 3's bytes, and which record 0023 and its sketch give as a list.

A change to the teams file's shape, a version among it, changes the module and its pinned file in the same change (`flake.2`), as `code.8` holds the mod to what crew models.

### Decision 3: the file is `builtins.toJSON` of the settings, the fleet's bytes

The module renders the file at evaluation (`nix/modules/json.nix`): every key whose value is null left out, at any depth, lists included, then `builtins.toJSON`, with no newline added. `builtins.toJSON` sorts each object's keys and adds no space, which is what `teamsJsonFor` writes: for the same partitions in the same order the module's file is byte for byte deneb's today, pinned as `nix/tests/files/deneb.json`. So a host moving from the fleet's file to the module's changes no byte crew reads, and crew's follower, which watches the file's bytes (`board.moved_at`), refreshes nothing for it. The file is `pkgs.writeText "crew-teams.json"`. Not taken: `pkgs.formats.json`, which renders through jq in a build, so the gate could compare no text without building, and pretty-prints, changing every byte.

### Decision 4: the activation links the file for the user who runs crew

crew reads `~/.config/crew/teams.json` from its own home, so the module writes into a user's home. `nix/modules/activate.sh link <file> <host>` links that path to the module's file: a link there is replaced; a file or folder there that is no link is moved once to `teams.json.before-nix`, both named; where that is taken, it changes neither, names both and exits 1. It says a line only where it moved or linked something. This is Boomdrive's `activate.sh link`, for crew's path, and like home-manager's file today the path is a link into the store.

- **nix-darwin**: as nix-darwin's primary user (`system.primaryUser`, required by the module), under their home, in `system.activationScripts.postActivation`: `sudo --user=<user> -- /usr/bin/env HOME=<home> /bin/sh <activate.sh> link <file> <host> || true`. A primary user with no `users.users.<user>.home` fails evaluation naming it.
- **NixOS**: `services.crew.user`, no default; `system.userActivationScripts.crew` runs the link only when `id -un` is that user, with the system's shell. Every user's activation runs it at their manager's start and at a switch, so the link is made when that user's processes, crew among them, can run; nothing lingers for it. A user `users.users` does not declare fails evaluation naming `services.crew.user` and `users.users.<user>`.

`|| true` on both: a link that fails says why and stops nothing else of the system's activation. Not taken: a home-manager module, which a nix-darwin or NixOS host need not run (Boomdrive's modules are system modules); a real file written by `install` and moved over, as the fleet writes Flume's file: crew reads bytes, never a link's mode, and a link names the generation that wrote it.

### Decision 5: `services.crew.host` names the host, and the activation holds crew to it

The host is not written into the file: crew reads its host from `hostname -s` and record 0023 changes nothing crew reads, so a `host` key would be a second name for the host that crew ignores. The Boomdrive module reads the option. Since crew and the derived crew table must agree on the name, `activate.sh link` reads the host's own name as `hostname -s` gives it, `uname -n` up to its first dot (NixOS's user activation has coreutils on its path and no `hostname`), and where it is not `<host>` says one line naming both, after linking. It never fails for it: the file is right either way, and the line tells the person whose name to fix. Not taken: crew reading `host` from the file, a change to crew's reading record 0023 rules out; a default from `networking.hostName`, which nix-darwin leaves null and NixOS defaults to `nixos`.

### Decision 6: the package in the system profile, and nothing else on the host

`environment.systemPackages = [ cfg.package ]`. The module adds no file under `/etc`, no launchd agent or daemon, no systemd unit and no user setting: crew runs no service (`state.4`), and the hosts file stays the fleet's (principle 10, `code.5`). A case compares a system with the module enabled against the same system with it not enabled. Not taken: writing `~/.config/swancloud/herdr-hosts.json`, swancloud's file, which names herdr's sessions and spaces; a `package = null` that installs none, which leaves the Boomdrive module no plugin path to read.

### Decision 7: the flake's checks are the moon project `nix`, offline and read-only

`.moon/workspace.yml` lists `nix: 'nix'`. `nix/moon.yml`, run from the workspace root, tags each task `check-full`, which crew's policy requires of `bolt/*`, `main` and `teamless/deneb`, so sluice runs them on every submission they are affected by and `tests/suite` beside the suite (`tests.5`):

- `format`: `nixfmt --check` over `flake.nix` and every `.nix` file under `nix/`.
- `lint`: `statix check` and `deadnix --fail` over the same.
- `typecheck`: `sh nix/check.sh typecheck`: every package of every system evaluates to a derivation, and each module evaluates in a minimal system of its platform.
- `test`: `sh nix/check.sh test`: the cases under `nix/tests/`, then `nix/tests/activate.sh`.

`nix/check.sh` is Boomdrive's: `nix eval --raw --offline --read-only --impure --store 'dummy://?store=/crew-check/store' --file nix/tests <check>`, with nix's configuration, caches and state in a scratch folder, so it computes every path and writes none, needs no network and no daemon, and touches nothing of the host's (`tests.11`: it reaches no other host). Each failure is one line, `nix: <case>: <what>`, and every case runs. The inputs are read where the devenv shell fetched them: `nix/inputs.nix`, Boomdrive's, turns `flake.lock` into the inputs `flake.nix`'s outputs take, by `builtins.fetchTree` in the shell and by the store paths of `CREW_FLAKE_INPUTS` in the check, and `devenv.nix` sets `env.CREW_FLAKE_INPUTS` from it. Each task's inputs are what its outcome depends on (`tests.10`): the flake's files, the devenv files, and, for `typecheck` and `test`, `plugin/lib/crew.py`, whose version the module reads; the package's other files move its path but no case's outcome. crew's devenv carries nix, nixfmt, statix and deadnix from its own nixpkgs, pinned by `devenv.lock` as jq and recutils are (`code.1` amended).

The pinned file is checked from both sides: the nix project's test holds the module's file to `nix/tests/files/deneb.json` byte for byte, and crew's logic tier loads that same file with `crew.load`, so the module writes what crew reads. Not taken: building the package or a system in the check, which needs each platform's builder and the network; a flake check (`checks.<system>`), which `nix flake check` runs only by building; a contract test running nix, since the flake's checks are its own project's, not a pin of crew's assumptions.

### Decision 8: `tests/suite` runs every project's `check-full` tasks

`tests/suite` with no name selects every project's `check-full` tasks, as sluice's `#check-full` does, so a coder's `tests/suite --affected` runs the flake's checks a change touches. A name holding a colon is `<project>:<task>`, refused unless that project's `moon.yml` has the task; every other name keeps its meaning (`logic`, `contract`, `mod`, a test). A task of `tests` is reported by its name as today, another project's as `<project>:<task>`, its failure output read from moon's state for that project. `tests/t-suite.sh` proves it on a stand-in project `nix` in its scratch workspace.

### Decision 9: the record and the rules

These choices are record 0058, the construct stage's own on record 0023, each cheap to change, with the paths not taken. `docs/architecture/flake.md`, loaded for `flake.nix`, `flake.lock` and `nix/`, adds `flake.1` (what the flake gives and the module writes), `flake.2` (the file's keys, version and bytes) and `flake.3` (the checks); `code.1` names the flake's tools in crew's devenv; `code.5`'s details name the module among the writers of the teams file; `tests.5` counts the flake's tasks among the `check-full` tasks. All are in this change's own commit, each marked not built until it lands.

## Risks / Trade-offs

- **A host's own package from another commit than the module.** The module writes the version of its own commit's crew; a host's own crew that reads another refuses the file at load, naming its version (`read.1`). A host takes the module and the package from one crew, as the fleet will by taking crew's flake as its input.
- **The hosts file is still the fleet's.** A host configured only through the module still needs `~/.config/swancloud/herdr-hosts.json` for `crew.load`; until crew stops reading it, a host outside the fleet writes it by hand.
- **The first entry into crew's shell after `flake.lock` moves fetches the inputs.** devenv's evaluation fetches nixpkgs and nix-darwin once per lock, as Boomdrive's shell does; an entry with no network then fails the flake's checks for want of them, and every other command waits on the fetch once.
- **The flake follows `teamless/deneb`.** The flake is built on `teamless/deneb`, whose crew reads version 5, so the Boomdrive flake takes it at a commit of that branch, as swancloud pins deneb's crew, until the refactor returns to main.
- **Two writers for one path while swancloud moves.** A host that enables the module while home-manager still writes `crew/teams.json` has two writers of one link; swancloud drops its entry in the deploy that enables the module, and home-manager leaves a link it did not make.

## After deploy

None: this change moves nothing on any host. A host takes the module only through its own configuration's change, Boomdrive's re-export and swancloud's move to the options, each with its own checks.
