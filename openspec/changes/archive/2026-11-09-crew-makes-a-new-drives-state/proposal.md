# crew makes a new drive's state

## Why

A person whose Mac Nix does not manage installs Boomdrive's programs with `nix profile add` and runs Boomdrive's setup, which "does the rest" (agentplot/boomdrive record 0009, amendment of 2026-11-09, the user's choice on their card that day). Among what setup leaves: "crew's file names this drive and its state, so the person can start crew's agents and talk to them." That record asks crew to "make a new drive's state and name the drive in its own file at setup's asking, since crew alone knows its state's layout."

crew has no command for it. `crew state init <label>` makes `<label>/main`, but only for a drive the teams file already names, and nothing of crew's writes the teams file: `code.5` had crew never write it, and crew's module writes it only where Nix configures the host (record 0058). crew now reads every fact of a host's drives from its own teams file alone (record 0064, built by `crew-runs-from-its-own-file-alone`, landed on this bolt at f564d22), and `code.5` as amended with it lets crew's own command write the file "at setup's asking where Nix does not link it". This change builds that command.

## What Changes

- New command `crew drive set <label>`, run on the host it is invoked on and never forwarded. Each key crew's module writes for a drive, and for the hosts and this host's consoles and kept repositories the drive needs, is a flag, with no default: `--state`, `--blueprints`, `--machine`, `--session`, `--folder`, `--repos`, `--accounts`, `--flume`, `--review` and `--hosts`, each required; `--roles`, `--console` and `--repositories`, each optional as in the module. `--json` answers in one JSON object.
- It writes the drive's entry into `~/.config/crew/teams.json`, its console and this host's kept repositories for it, keeping every other drive, host, console and kept repository the file names, and writes the file as crew's module writes it: the same bytes for the same settings. It checks the file it would write as crew loads it, and refuses with nothing written.
- It then makes `<label>/main` in the drive's state repository, the same starting files `crew state init` makes, after checking the repository can be reached and before writing anything. A branch that exists stays as it is.
- Where Nix links the teams file, it writes nothing there and says so. It makes the drive's state only where the linked file already names the drive with the facts given; otherwise it refuses, naming each fact that differs and `services.crew.settings.drives.<label>`.
- A teams file crew cannot load is moved aside once, to `teams.json.before-drive-set`, and both paths are named, as crew's module moves a file aside. Where that path is already taken, nothing is written.
- Run again with the same answers, it changes nothing: no byte of the file, no commit, no entry. Where it changes the file, one `drive.set` entry on the drive's branch names the drive, the keys it changed and who ran it.
- Every refusal of the teams file, a missing file among them, names `crew drive set` beside crew's module and the machine's configuration as the file's writer.
- The operator's brief says that, on a host Boomdrive's setup set up, a drive changes through setup, which writes crew's entry with `crew drive set`, and never by a hand edit of the teams file.

## Capabilities

### New Capabilities

- `drive-setup`: `crew drive set`, which names a drive in the host's teams file from its flags and makes the drive's state, at setup's asking on a host Nix does not configure.

### Modified Capabilities

- `main-level`: the teams file's writer, named in every refusal of it, includes `crew drive set`, and a missing teams file is refused naming it.
- `operator-agent`: the operator's brief says how a drive changes on a host Boomdrive's setup set up.
