# Design: crew reads its release where it runs from one

## Context

crew finds its root from its own file, `HOME = LIB.parent.parent` (`crew.py`), and names its own command by it wherever it hands one on: every brief's `{{TEAM_CMD}}`, `SENDS` and roster (`main_tokens`), `crew_on` for this host, the Stop hook's hand to `crew _renew` (`hold.hand`), the follower's Pending You notice and its `_update` (`board.notice_argv`, `Follower.again`), and the console's tabs (`plan.console_cmd`). From a checkout that path moves with the checkout. From a build it is a store path, which names one build forever.

What a host runs, read on deneb 2026-11-08: the `crew` on the user's path is `/etc/profiles/per-user/chuck/bin/crew`, a link the user profile's activation moves, to a wrapper that execs `/nix/store/1gmha0787…-crew-0.41.0-unstable-2026-11-07/plugin/bin/crew`; `/run/current-system/sw/bin/crew` does not exist. A standing agent's session was started with `--plugin-dir /nix/store/7292pjr3…-crew-0.41.0-unstable-2026-11-07/plugin`, an older build, and its brief names that build's command. Claude Code runs a plugin's hooks from the folder the session loaded (`${CLAUDE_PLUGIN_ROOT}`, `plugin/hooks/hooks.json`), so the Stop hook, the session-start hook and the card and question hooks of that session run the older build's code until the session starts again.

crew reads what it is from git alone: `crew_version` runs `git describe` in `HOME`, and in a build there is no git, so a start there records no commit (`plugin/hooks/session-start` `loaded`), and `update_due` reads it by its launch digest alone (`NO_COMMIT_SAID`; record 0050 as amended 2026-10-30; `teams.19`'s reading of that day). The launch digest already reads crew's own root in a brief as one word, so a host's two crews, a checkout and a build, digest one start alike (`launch_digest`; `teams.19`'s reading of 2026-10-31).

crew's flake builds crew's package from the tree's `plugin/` and a `bin/crew` wrapper (`nix/packages/crew.nix`, record 0058, `flake.1`); its version is nixpkgs' form for an untagged commit, `0-unstable-<date>`, since crew keeps its version in no file (`code.10`). A flake knows the commit it is built from as `self.rev`, absent for a tree with uncommitted changes, and never a tag.

Record 0050 as amended 2026-11-08 asks for two things: a standing agent's crew commands run the crew the host has installed now, and crew knows the release it runs from, so a change to what a session loads makes each standing agent due a restart at its next stop.

Rules this design relies on: `teams.19` (a standing agent due a restart when its brief, model, effort or folders, or the part of crew's plugin a session loads, changed; restarted at its next stop; never for crew's code alone, which every command runs live), `teams.6` (a start records what it loaded, `CREW_COMMIT`, `CREW_VERSION`, `CREW_LAUNCH`), `read.1` (what crew can't read makes nothing due and is said), `read.2` (another crew's answer read by checked fields), `code.1` (standard library only), `code.7` (each decision a function of plain facts), `code.9` (a read of another process is bounded), `code.10` (no version kept in a file of the tree), `code.11` (`-h` answered first), `state.4` (nothing written for a view), `flake.1` and `flake.3` (the package; the checks evaluate and build nothing), `plan.19` (hosts run crew released), `tests.4`, `tests.11` and `tests.12` (each case in the lowest tier). Pages whose areas it touches: `teams.md` (`crew.py`, `plugin/bin/crew`), `plan.md` (`plan.py`'s console), `flake.md` (`flake.nix`, `nix/`), `tests.md` (`tests/`), `docs.md` (README, `openspec/`). It departs from no rule. Two readings follow from it for the design agent after the landing (`docs.7`): `teams.19`'s details, that on a build the part of crew's plugin a session loads is the build's folder whole, since its hooks run from it, so a release other than the start's is a change to it, and that `NO_COMMIT_SAID`'s "until crew reads its release where it runs" is built; and `flake.1`, that the package also carries `plugin/release.json`, a file of the build alone and never of the tree, so `code.10` holds.

## Goals / Non-Goals

**Goals:** every crew command a standing agent runs, and every process crew hands its command to, runs the crew its host has installed now; a build knows its commit and version; a standing agent is due a restart at its next stop once the host installs a crew whose loaded plugin differs from the one its session started on, judged by the installed crew whichever build the judging hook runs from; the follower catches an idle one when an install moves.

**Non-Goals:** the plugin a session loads, and the `crew` a host installs, which are the host configuration's (`--plugin-dir`, the user's or the system's profile), Boomdrive's module or swancloud's; a release file in a package other than crew's flake's; a tag in the release file, which a flake cannot know; the card and question hooks of a running session, which run its loaded build until its restart, as today; another tool's pinned paths.

## Decisions

### Decision 1: crew reads what it is where it runs

`crew_read(root)` says what a crew root is, as facts: `{"root", "commit", "version", "from", "unread"}`. Where `root/.git` exists, a folder or a linked worktree's file, it is a checkout: the commit and version as `crew_version` reads them today, `from` `"checkout"`. Otherwise, where `root/plugin/release.json` exists, it is a build: the file's commit and version, `from` `"release"`. Otherwise nothing, `from` null, `unread` saying there is neither git nor a release file. Whether `root` is a checkout is read from `root/.git` and never from git's search upward, so a build kept in a folder under some repository is never read as that repository. `crew_version(root)` keeps its shape, `(commit, version)`, from `crew_read`, so the session-start hook records a build's release with no change of its own.

`release_read(text)` checks the file: a JSON object whose `commit` is forty hexadecimal characters and whose `version` is a non-empty string; anything else reads as no release, saying what the file lacks (`read.2`). `release_version(version, commit)` gives the version crew shows, as `git describe` gives a checkout's: `v<x.y.z>` where the package's version is a release's, `x.y.z` alone, and otherwise the version, `+` and the commit's first seven characters, `0-unstable-2026-11-08+fcedc22`, so two builds of one day read apart. Not taken: the version alone, which reads two builds of a day alike in a band.

### Decision 2: crew's package carries its release

`nix/packages/crew.nix` takes `commit ? null`, and `flake.nix` passes `self.rev or null`. Where a commit is given, the package's `release` is `{ commit; version; }`, its own `version` argument, so a host that overrides the version carries what it overrode, and its install writes `builtins.toJSON release` to `$out/plugin/release.json`; where none is, `release` is null and no file is written, so a build from a tree with uncommitted changes reads as carrying no release rather than as the commit below them. `passthru.release` exposes it, so the flake's checks read it by evaluation alone (`flake.3`). The file lives in the build, never in the tree, so no version is kept in a file of crew's (`code.10`); it sits under `plugin/` beside the code that reads it, in the folder a session loads. Not taken: `self.dirtyRev`, which names a commit the build does not hold; a tag, which a flake cannot see.

### Decision 3: the installed crew is a checkout's own, else the first `crew` on the path outside the store

`installed_command(home, checkout, found)` decides, on plain facts (`code.7`), the command of the crew the host has installed: where crew runs from a checkout, `home/plugin/bin/crew`, the checkout being what this host runs and moves; otherwise the first of `found`, the folders of crew's path in their order that hold an executable `crew`, that lies outside the Nix store, `/nix/store/`; otherwise None. A folder outside the store is a profile's link, `/etc/profiles/per-user/<user>/bin`, `~/.nix-profile/bin` or `/run/current-system/sw/bin`, which each install moves to the crew it installs, or a host's own link to a checkout; a folder inside the store names one build forever, as a session's shim, a plugin's `bin/` or a pinned wrapper does, and is passed over. `crew_command()` is that command, or the build's own `plugin/bin/crew` where there is none.

Not taken: a bare `crew` in a brief, which a session resolves on a path that may carry store folders first; a fixed profile list, which would guess where the host puts crew where its path already says (deneb's crew is in the user profile, its system profile has none); the system profile alone, which no host of the fleet installs crew in yet.

### Decision 4: every command crew hands on names the installed crew

`crew_command()` replaces `HOME / "plugin/bin/crew"` wherever crew names its command for a later run: `main_tokens`'s `TEAM_CMD`, which every brief, `signal_how`, `cards_how` and the roster are built from; `SENDS`, which becomes a function of it; `crew_on` for this host, which forwarded commands run; `hold.hand`'s `_renew`; `board.notice_argv`; `Follower.again`'s `_update`; and `plan.console_cmd`'s tabs, whose shell tab's path takes the command's folder. So an agent's command, the restart its Stop hook hands, and each notice the follower's watch runs, all start the crew installed now. `crew-role` stays `HOME`'s: every process that starts an agent is already one of the installed crew, reached through a brief, a hand or the user's path.

### Decision 5: one word for crew's command in the launch digest

`launch_digest` reads every path a brief may name crew's command by, `crew_command()` and the root's own `plugin/bin/crew`, as the one word `<crew>`, then any other mention of the root as `<crew-home>`, before it digests. So a brief a build built, naming the installed command, and the same brief a checkout of the host built, naming its own, digest alike (`teams.19`'s reading of 2026-10-31 holds). Every start recorded before this change digested its brief with `<crew>/plugin/bin/crew`, so each reads as due once, its brief changed: that restart is what gives each standing agent a brief naming the installed crew, and it needs nothing of its own.

### Decision 6: `crew _release`, and how one crew reads another

`crew _release` prints `crew_read()` of its own root as one line of JSON and does nothing else: `plugin/bin/crew` sends it to `crew.py` before anything is read, forwarded or checked, and `crew.py` answers it before it loads the teams file; `-h` and `--help` print its usage (`code.11`). It is the one way a crew reads another crew it cannot import, whatever wrapper stands between the path and the plugin.

`installed()` reads the installed crew as facts of `crew_read`'s shape. Where the installed command is crew's own, a checkout's `plugin/bin/crew` or a command whose real path is the root's `bin/crew` or `plugin/bin/crew`, it is `crew_read()` with no process. Where there is no installed command, it is unread, saying no folder of the path outside the Nix store has a `crew`. Otherwise it runs `bash <command> _release` with a bound of five seconds (`code.9`), inside the Stop hook's ten, and reads its line with `release_said(text)`, which checks each field and reads a missing or malformed one as unread (`read.2`); a command that does not answer in time, exits non-zero or prints no such line is unread, saying which (`read.1`). The answer is kept for the process by the command's real path, so a long-lived follower asks again only when an install moves that path, and a one-shot command asks at most once.

### Decision 7: the update check reads the installed crew

`update_due(started, installed, launch, loaded)` decides, in order: no recorded start, not due; a start with no launch, due, started before crew kept what an agent loads; a launch that differs, due, its brief, model, effort or folders changed; a start with no commit, not due, `NO_COMMIT_SAID`, which now says the start recorded no release of crew's, so `crew main down` and `crew main up` restart it on the crew this host has installed; an installed crew unread, not due, crew saying it can't read the crew this host has installed and why; the same commit, not due; an installed checkout, due as today when what a session loads changed between the two commits (`loaded_changed` in the installed root), not when only code did, and saying it can't tell when git can't; an installed build, due, crew's release changed. A build's release differing is a change to what the session loaded, since the session loaded the build's folder whole and its hooks run from it; git is not there to say which files moved.

`due_of` reads `installed()` and passes it, and `loaded_changed` runs in the installed root only for an installed checkout. Its callers judge against the installed crew: the Stop hook, `board.here_read`, `hold.update_here` and `hold.renew`, whose notice names the installed version. The Stop hook of a session that loaded an older build still runs that build's code, but from the first build carrying this change on, that code asks the installed crew, so it sees the install whichever build it is.

### Decision 8: the follower watches the installed crew

`board.moved_at` reads crew's stamp as `crew_stamp()`: the checkout's commit (`head_here`) where crew runs from a checkout, as today; else the real path of the installed command, a read of links with no process; else None, which `refresh_plan` already reads as unread and acts on with no update (`read.1`). An install moves the real path, so the next refresh is an update: `Follower.again` runs `_update` through the installed command, which hands each due agent its restart, idle ones among them, and starts again through the installed command's `_follow` when that command is not crew's own, handing on its lock as it does today; where it is its own, it starts again as today.

### Decision 9: the band shows the installed release

`board.here_read` gives the host's version from `installed()`, so a band's "→ <version> at its next stop" names the release the agent will take; an agent's own version is what its start recorded, as today. The views keep their shape, so the mod draws them unchanged (`code.8` not reached).

## Risks / Trade-offs

- **Every release restarts every standing agent on a build host.** Each install of another release makes each standing agent due at its next stop, with its conversation, told what changed, which is what `teams.19` gives an update; git is not there to narrow it to the releases that changed what a session loads, and the session's hooks run from the folder it loaded, so no release leaves the session's loaded code as it is.
- **A process at each turn's end on a host whose installed command is a wrapper.** Where the installed command is no layout of crew's own, as swancloud's `crewCommand` is, the Stop hook asks it `crew _release` once per turn's end, bounded at five seconds; a long-lived process keeps the answer by the command's real path.
- **A host whose sessions load a plugin with no release file** keeps today's reading: its starts record no commit, `NO_COMMIT_SAID` says so, and an install makes an agent due only when it changes its brief. The commands' half of this change holds on such a host at once. It ends once the host's sessions load crew's flake package, which is the host configuration's.
- **A path with no profile holding crew** names the build's own command, as today, and reads the installed crew as unread, saying so; such a process makes no agent due for crew's plugin.
- **The first restart after the landing.** Every standing agent is due once on its host's first crew carrying this change, its digest's word for crew having changed (Decision 5).
- **The store is `/nix/store`.** A host with another store folder would have its store folders read as installed. No host of the fleet has one.

## After deploy

On each host, once its installed crew carries this change (`crew _release` through the user's path answers), ops or the operator of a partition whose main level runs there:

1. Runs `crew update <host>`, which hands each standing agent started before it its restart. No check can do this: those agents' Stop hooks run the build they started on, which reads no installed crew, so no code of this change runs in them until they start again.
2. Starts the host's follower again once, swancloud's `crew-follow` job where it runs, or the console's rail tab where no job does, unless the deploy that installed the crew already did. No check can do this: the follower running then is a build without this change, which does not watch the installed crew; from its next start it does.
